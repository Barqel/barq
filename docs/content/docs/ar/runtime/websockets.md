تتيح لك اتصالات WebSocket بناء ميزات تحتاج إلى تبادل البيانات في الوقت الفعلي، مثل المحادثات المباشرة والإشعارات الفورية ولوحات المتابعة الحية.

تعتمد واجهة WebSocket في Barq على محرك Bun الأصلي، ولذلك تتوفر عند تشغيل التطبيق على Bun فقط؛ إذ لا ينفذ محوّل HTTP في Node.js ترقية WebSocket. على Bun، يمكنك تحديد المسار والتحقق من الطلب قبل ترقية الاتصال وتمرير بيانات المستخدم إلى معالجات الأحداث وضبط حدود الموارد.

## إنشاء اتصال WebSocket

استخدم `app.ws()` لتسجيل مسار WebSocket وتحديد معالجات الأحداث التي تنفذها عند فتح الاتصال أو استقبال رسالة أو إغلاق الاتصال.

في المثال التالي، ينشئ التطبيق نقطة اتصال للمحادثة على المسار `/chat`:

```ts
import { App, type WebSocketHandlers } from "@barqel/barq";

interface SocketSession {
  userId: string;
  role: string;
}

const handlers: WebSocketHandlers<SocketSession> = {
  open(ws) {
    console.log(`Connected: ${ws.data.userId}`);
    ws.send(`Welcome ${ws.data.userId}!`);
  },

  message(ws, msg) {
    ws.send(`Echo: ${msg}`);
  },

  close(ws, code, reason) {
    console.log(`Disconnected: ${ws.data.userId}`);
  },
};

const app = new App();

app.ws(
  "/chat",
  handlers,
  (ctx) => {
    const token = ctx.queryParam("token");

    if (!token) return false;

    return {
      data: {
        userId: "user_42",
        role: "moderator",
      },
    };
  },
);

app.listen(3000);
```

يشرح هذا المثال ثلاثة أجزاء أساسية: بيانات الجلسة، ومعالجات الأحداث، والتحقق من الطلب قبل ترقية الاتصال.

## فهم معالجات الأحداث

تحدد `WebSocketHandlers<SocketSession>` الدوال التي يتعامل بها التطبيق مع دورة حياة الاتصال.

### `open(ws)`

تعمل عند فتح اتصال WebSocket بنجاح.

في المثال، يقرأ المعالج `ws.data.userId` لإظهار هوية المستخدم، ثم يرسل إليه رسالة ترحيب:

```ts
open(ws) {
  console.log(`Connected: ${ws.data.userId}`);
  ws.send(`Welcome ${ws.data.userId}!`);
}
```

يمكنك استخدام هذا الحدث لتهيئة حالة الاتصال أو إرسال رسالة أولية إلى العميل.

### `message(ws, msg)`

تعمل عند استقبال رسالة من العميل.

```ts
message(ws, msg) {
  ws.send(`Echo: ${msg}`);
}
```

يعيد المثال الرسالة إلى المرسل مع إضافة `Echo:`، وهو أسلوب بسيط لاختبار الاتصال. في التطبيق الفعلي، يمكنك تحليل الرسالة والتحقق من محتواها ثم تنفيذ الإجراء المناسب.

لا تفترض أن كل رسالة نصية أو بيانات واردة موثوقة. تحقّق من نوع الرسالة وبنيتها وصلاحيات المستخدم قبل تنفيذ العمليات الحساسة.

### `close(ws, code, reason)`

تعمل عند إغلاق الاتصال، وتستقبل رمز الإغلاق وسببه إلى جانب كائن الاتصال.

```ts
close(ws, code, reason) {
  console.log(`Disconnected: ${ws.data.userId}`);
}
```

يمكنك استخدام هذا الحدث لتنظيف حالة الاتصال أو تسجيل سبب الإغلاق. إذا كان تطبيقك يحتفظ بقائمة للمستخدمين المتصلين، فاستخدم حدث الإغلاق لتحديثها عند الحاجة.

## التحقق من المصادقة قبل ترقية الاتصال

يتيح لك الوسيط الثالث في `app.ws()` تمرير دالة `beforeUpgrade` للتحقق من الطلب قبل إنشاء اتصال WebSocket.

```ts
app.ws(
  "/chat",
  handlers,
  (ctx) => {
    const token = ctx.queryParam("token");

    if (!token) return false;

    return {
      data: {
        userId: "user_42",
        role: "moderator",
      },
    };
  },
);
```

في هذا المثال:

1. يقرأ `ctx.queryParam("token")` قيمة `token` من معاملات عنوان الطلب.
2. إذا لم توجد قيمة، تعيد الدالة `false` لرفض الترقية.
3. إذا اجتاز الطلب الفحص، تعيد الدالة كائنًا يحتوي على `data`.
4. تُستخدم بيانات الجلسة لتمرير معلومات المستخدم إلى معالجات WebSocket عبر `ws.data`.

**مهم:** وجود الرمز وحده لا يعني أن المستخدم موثوق. في التطبيق الحقيقي، تحقّق من صحة الرمز وتوقيعه وانتهاء صلاحيته وصلاحيات صاحبه قبل قبول الاتصال. يعرض المثال موضع إجراء التحقق، ولا ينفذ تحققًا كاملًا من الرمز.

### تمرير بيانات الجلسة

تتيح لك `SocketSession` تحديد شكل البيانات المتاحة للمعالجات:

```ts
interface SocketSession {
  userId: string;
  role: string;
}
```

ثم تعيدها دالة `beforeUpgrade` ضمن `data`:

```ts
return {
  data: {
    userId: "user_42",
    role: "moderator",
  },
};
```

بعد ذلك، يمكن لمعالجات الأحداث قراءة القيم من `ws.data`:

```ts
open(ws) {
  console.log(ws.data.userId);
  console.log(ws.data.role);
}
```

يساعد هذا الأسلوب على تمرير معلومات الجلسة إلى المعالجات دون الحاجة إلى إعادة استخراجها من الطلب في كل حدث.

تذكّر أن `userId` و`role` في المثال قيم ثابتة للتوضيح. في التطبيق الحقيقي، ينبغي أن تأتي بيانات الجلسة من نتيجة المصادقة الفعلية، لا من قيم يحددها العميل أو من بيانات ثابتة في الشيفرة.

### مثال على طلب الاتصال

يمكن للعميل طلب المسار `/chat` مع تمرير رمز في عنوان الاتصال:

```ts
const socket = new WebSocket(
  "ws://localhost:3000/chat?token=YOUR_TOKEN",
);
```

استبدل `YOUR_TOKEN` برمز مناسب لبيئة التطبيق. لا تستخدم رمزًا حقيقيًا في أمثلة عامة أو مستودعات مفتوحة.

ضع في اعتبارك أن رموز المصادقة في عناوين URL قد تظهر في سجلات الخوادم أو أدوات المراقبة. إذا كان تطبيقك يتعامل مع بيانات حساسة، فاختر طريقة مصادقة مناسبة لبيئتك، وراجع ما إذا كان Barq يدعم تمرير بيانات المصادقة عبر ترويسات طلب الترقية.

## ضبط حدود الرسائل والموارد

تتيح لك خيارات `websocket` تحديد حدود تساعد على التحكم في حجم الرسائل والبيانات المعلقة ومدة الخمول:

```ts
const app = new App({
  websocket: {
    maxPayloadLength: 64 * 1024,
    backpressureLimit: 256 * 1024,
    idleTimeout: 60,
  },
});
```

القيم في المثال توضيحية. اخترها وفق طبيعة الرسائل وعدد الاتصالات المتوقع، وتأكد من توافقها مع خيارات WebSocket التي يدعمها إصدار Barq المستخدم.

### `maxPayloadLength`

يحدد الحد الأقصى لحجم الرسالة الواردة، بالبايت، وفق سلوك الإعداد المستخدم.

في المثال:

```ts
maxPayloadLength: 64 * 1024
```

القيمة تساوي 65,536 بايت، أي 64 KiB.

اختر الحد بناءً على حجم البيانات التي يتوقعها التطبيق. لا تجعل الرسائل أكبر مما تحتاج إليه؛ فالحد المناسب يساعد على الحد من استهلاك الموارد الناتج عن الرسائل الضخمة.

### `backpressureLimit`

يحدد الحد المسموح به للضغط الناتج عن تراكم البيانات التي لم تُرسل بعد، وفق تطبيق Barq.

```ts
backpressureLimit: 256 * 1024
```

تعادل القيمة 256 KiB.

قد يحدث الضغط عندما يرسل الخادم البيانات بسرعة أكبر من قدرة العميل على استقبالها. يساعد وضع حد مناسب على التحكم في حجم البيانات المعلقة، لكن عليك التأكد من السلوك الفعلي عند بلوغ الحد: هل تُرفض الرسائل أم تُسقط أم يُغلق الاتصال؟

لا تفترض أن هذا الخيار يضمن تسليم جميع الرسائل. إذا كانت الرسائل مهمة، فصمّم بروتوكول التطبيق بحيث يتعامل مع الفشل أو إعادة الاتصال أو تأكيد الاستلام عند الحاجة.

### `idleTimeout`

تحدد هذه القيمة مهلة الخمول بالثواني وفق إعداد WebSocket المستخدم:

```ts
idleTimeout: 60
```

في هذا المثال، القيمة 60 ثانية.

اختر المهلة بما يناسب طبيعة الاتصال. قد تحتاج المحادثات أو لوحات المتابعة إلى اتصالات طويلة العمر، بينما قد ترغب في إنهاء الاتصالات الخاملة لتقليل استهلاك الموارد.

تحقّق من تعريف `idleTimeout` في تنفيذ Barq وإعدادات Bun للتأكد من المقصود بالخمول، وما إذا كانت الرسائل أو إشارات الاتصال الدورية تؤثر في احتساب المهلة.

## أفضل الممارسات

- تحقّق من هوية المستخدم وصلاحياته قبل قبول اتصال WebSocket.
- لا تعتبر وجود `token` دليلًا كافيًا على صحة المصادقة.
- استخدم `SocketSession` لتعريف بيانات الجلسة المتاحة لمعالجات الأحداث.
- تحقّق من محتوى الرسائل الواردة قبل تنفيذ العمليات الحساسة.
- اضبط `maxPayloadLength` وفق حجم الرسائل المتوقع.
- اضبط `backpressureLimit` بما يتناسب مع معدل الإرسال وقدرة العملاء على الاستقبال.
- اختر مهلة خمول مناسبة، واختبر سلوك الاتصال عند انقطاع الشبكة وإعادة الاتصال.
- لا تسجّل الرموز السرية أو بيانات المصادقة الحساسة في السجلات.
- اختبر سلوك حدود الموارد عمليًا قبل اعتماد القيم في بيئة الإنتاج.
