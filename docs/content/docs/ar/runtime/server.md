يمنحك Barq تحكمًا مباشرًا في إعداد خادم HTTP ودورة حياته، بدءًا من عنوان الاستماع وحدود الموارد، وصولًا إلى الإيقاف المنظّم عند إعادة تشغيل التطبيق أو نشر إصدار جديد.

في هذا الدليل، ستتعلم كيفية إعداد الخادم، والتعامل مع إشارات الإيقاف، وتشغيل عدة عمال على Linux.

> **اختلاف بيئة التشغيل:** يدعم Node.js بروتوكول HTTP عبر `@barqel/barq/node`، ويستخدم خياري `hostname` و`port`. أما TLS وحدود خادم Bun وWebSocket وتشغيل العمال المتعددين و`app.stop()` فهي ميزات خاصة بـBun. يعيد محوّل Node.js مقبضًا للخادم؛ استخدم `await server.stop()` لإغلاقه. لا يوفر المحوّل إيقافًا سلسًا ينتظر انتهاء الاتصالات الجارية.

## إعداد الخادم

أنشئ التطبيق باستخدام `App`، ثم استدعِ `app.listen()` لبدء استقبال الطلبات.

```ts
import { App } from "@barqel/barq";

const app = new App({
  hostname: "127.0.0.1",
  port: 3000,
  idleTimeout: 30,
  maxRequestBodySize: 1_048_576,
  development: false,
});

const server = app.listen();

console.log(`Listening on ${server.hostname}:${server.port}`);
```

### فهم خيارات الخادم

| الخيار | الوظيفة | مثال |
| --- | --- | --- |
| `hostname` | عنوان الشبكة الذي يستمع عليه الخادم. | `127.0.0.1` للاستماع محليًا فقط. |
| `port` | منفذ الاستماع الافتراضي. | `3000` |
| `idleTimeout` | أقصى مدة مسموحة لاتصال خامل، بالثواني. | `30` |
| `maxRequestBodySize` | الحد الأقصى لحجم جسم الطلب، بالبايت. | `1_048_576`، أي 1 MiB. |
| `development` | يحدد ما إذا كان التطبيق يعمل في وضع التطوير. | `false` في المثال المخصص للتشغيل الفعلي. |
| `tls` | خيارات TLS التي يوفرها Bun لتشغيل HTTPS. | إعدادات الشهادة والمفتاح وفق واجهة Bun. |

تعرّف إلى الخيارات التي يحتاجها تطبيقك فعلًا، ولا ترفع حدود الموارد دون سبب واضح.

### اختيار عنوان الاستماع والمنفذ

يحدد `hostname` عنوان الشبكة الذي يرتبط به الخادم. على سبيل المثال:

- `127.0.0.1`: يقبل الاتصالات المحلية من الجهاز نفسه.
- `0.0.0.0`: يتيح الاستماع عبر واجهات الشبكة المتاحة، وفق إعدادات الشبكة والجدار الناري.

إذا أردت استقبال الاتصالات من أجهزة أخرى، فتأكد من أن عنوان الربط وقواعد الشبكة تسمح بذلك. لا تستخدم `0.0.0.0` لمجرد أنه الخيار الأسهل؛ اختره عندما تحتاج فعلًا إلى استقبال الاتصالات الخارجية.

يمكنك تحديد المنفذ في خيارات `App`:

```ts
const app = new App({
  hostname: "127.0.0.1",
  port: 3000,
});

const server = app.listen();
```

أو تمريره إلى `listen(port?)` مباشرة:

```ts
const server = app.listen(4000);
```

عند تحديد المنفذ في `listen(port?)`، تكون له الأولوية على قيمة `port` المحددة عند إنشاء التطبيق.

إذا لم تحدد منفذًا في أي من الموضعين، فقد يختار Bun منفذًا متاحًا تلقائيًا. لذلك، اقرأ `server.port` لمعرفة المنفذ الفعلي بدل افتراض أنه يساوي قيمة ثابتة.

### ضبط حدود الموارد

يؤثر كل من `maxRequestBodySize` و`idleTimeout` في كيفية تعامل الخادم مع الطلبات والاتصالات.

**`maxRequestBodySize` — الحد الأقصى لحجم الطلب**

تُقاس القيمة بالبايت. في المثال التالي، يُسمح بجسم طلب يصل حجمه إلى 1 MiB:

```ts
const app = new App({
  maxRequestBodySize: 1_048_576,
});
```

هذا الحد مهم عند استقبال JSON أو النماذج أو الملفات. اختر حجمًا يناسب طبيعة البيانات التي يستقبلها تطبيقك، وتجنب السماح بأحجام كبيرة دون حاجة؛ فالحد المناسب يساعد على تقليل استهلاك الذاكرة والموارد.

يجب أن تكون القيمة عددًا صحيحًا آمنًا غير سالب.

**`idleTimeout` — مهلة الاتصال الخامل**

تُقاس القيمة بالثواني، ويجب أن تقع بين `0` و`255`. القيمة `0` تعطل المهلة.

```ts
const app = new App({
  idleTimeout: 30,
});
```

اختر المهلة وفق طبيعة التطبيق والاتصالات التي يستخدمها. لا تفترض أن المهلة المناسبة لخادم HTTP عادي تناسب بالضرورة الاتصالات طويلة العمر، مثل WebSocket؛ راجع متطلبات كل نوع من الاتصالات وإعدادات Bun ذات الصلة.

### تشغيل HTTPS باستخدام TLS

يقبل الخيار `tls` إعدادات TLS التي يوفرها Bun، ولا ينفذه محوّل HTTP في Node.js. استخدمه عندما يحتاج تطبيق Bun إلى استقبال اتصالات HTTPS مباشرة:

```ts
const app = new App({
  port: 3000,
  tls: {
    // أضف خيارات TLS التي يدعمها Bun،
    // مثل مسارات الشهادة والمفتاح.
  },
});
```

المثال توضيحي؛ أضف قيم الشهادة والمفتاح الفعلية وفق إعدادات Bun وبيئة النشر لديك. لا تضع مفاتيح خاصة أو بيانات اعتماد حساسة في مستودع عام.

إذا كنت تنهي اتصالات HTTPS عند وكيل عكسي مثل Nginx أو عند منصة الاستضافة، فقد لا تحتاج إلى إعداد TLS داخل التطبيق نفسه.

## الإيقاف السلس

عندما يتلقى التطبيق إشارة إيقاف مثل `SIGINT` أو `SIGTERM`، فمن الأفضل إيقافه بطريقة منظّمة بدل إنهاء العملية فورًا. تنطبق `app.stop()` الموضحة هنا على خادم Bun.

استدعِ `await app.stop(hardTimeoutMs?)` لبدء الإيقاف وانتظر نتيجته:

```ts
let stopping = false;

async function shutdown() {
  if (stopping) return;
  stopping = true;

  const result = await app.stop(5_000);

  console.log("Stopped", result);
}

process.on("SIGINT", () => void shutdown());
process.on("SIGTERM", () => void shutdown());
```

يمنع المتغير `stopping` بدء عملية الإيقاف أكثر من مرة إذا وصلت إشارات متعددة. وتتيح المهلة البالغة `5_000` مللي ثانية خمس ثوانٍ قبل الوصول إلى حد الإيقاف الصلب.

### ماذا تعني نتيجة الإيقاف؟

تعرض النتيجة الحقلين التاليين:

- `forced`: يوضح ما إذا كان انتهاء المهلة الصلبة قد أدى إلى فرض الإيقاف.
- `pending`: يعرض معلومات عن الاتصالات المتبقية وفق نتيجة الإيقاف التي يعيدها Bun.

المهلة الافتراضية هي خمس ثوانٍ إذا لم تحدد قيمة أخرى.

لا يعني الإيقاف السلس أن كل طلب سيكتمل بالضرورة؛ فقد تبقى اتصالات أو أعمال قيد التنفيذ حتى انتهاء المهلة. لذلك، اختبر سلوك الإيقاف مع التطبيق الفعلي، خاصة إذا كان يتعامل مع طلبات طويلة أو مهام مهمة.

### متى تستخدم الإيقاف السلس؟

استخدمه عند:

- إعادة تشغيل التطبيق.
- نشر إصدار جديد.
- إيقاف الخدمة ضمن عملية نشر آلية.
- إنهاء التطبيق استجابةً لإشارات النظام.

في بيئة الإنتاج، تأكد أيضًا من أن مدير العمليات أو منصة النشر يمنح التطبيق وقتًا كافيًا للإيقاف قبل إنهاء العملية بالقوة.

## تشغيل عدة عمال على Linux

يوفر `app.cluster(port?)` أسلوبًا خاصًا بـBun لتشغيل عدة عمال على Linux. ينشئ التطبيق عامل Bun لكل معالج منطقي، ويستخدم `reusePort` لمشاركة المنفذ.

```ts
const app = new App();

app.cluster(3000);
```

استخدم منفذًا ثابتًا وغير صفري عند تشغيل `cluster()` على Linux.

يسمح تشغيل عدة عمال بمعالجة الطلبات عبر أكثر من عملية، وقد يساعد على الاستفادة من المعالجات المتاحة. لكن الأداء الفعلي يعتمد على طبيعة التطبيق، واستهلاك الموارد، ونوع الحمل؛ لذلك قِس النتائج بدل افتراض أن زيادة عدد العمال ستحسن الأداء دائمًا.

### ماذا يحدث على الأنظمة الأخرى؟

بحسب سلوك Barq الموضح هنا:

- **Linux:** يشغّل `cluster()` عدة عمال باستخدام `reusePort`.
- **macOS وWindows:** يبدأ `cluster()` مستمعًا واحدًا داخل عملية واحدة.

لذلك، لا تفترض أن استدعاء `cluster()` سيؤدي إلى إنشاء عدة عمليات على جميع أنظمة التشغيل.

### إيقاف الخادم

استخدم `app.stop()` لإيقاف الخادم وفق آلية الإيقاف التي يوفرها Barq:

```ts
await app.stop();
```

إذا كان التطبيق يشغّل عدة عمال، فتحقق من أن عملية الإيقاف تغطي العمال جميعًا في الإصدار المستخدم، واختبر ذلك ضمن بيئة النشر قبل الاعتماد عليه في الإنتاج.

## أفضل الممارسات

- اضبط `hostname` و`port` وفق بيئة التشغيل وطريقة استقبال الاتصالات.
- اختر حدًا مناسبًا لحجم جسم الطلب بدل السماح بطلبات ضخمة دون حاجة.
- اضبط مهلة الاتصالات الخاملة وفق طبيعة الخدمة.
- لا تعتمد على منفذ ثابت افتراضيًا إذا كان Bun يستطيع اختيار منفذ تلقائيًا في إعدادك؛ اقرأ `server.port`.
- تعامل مع `SIGINT` و`SIGTERM`، واختبر الإيقاف أثناء وجود طلبات قيد التنفيذ.
- استخدم `cluster()` على Linux عند الحاجة، ثم قارن الأداء الفعلي قبل وبعد تفعيله.
- احفظ الشهادات والمفاتيح والبيانات الحساسة خارج الشيفرة المصدرية.
