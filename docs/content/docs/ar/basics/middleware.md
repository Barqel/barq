عندما يكبر التطبيق، ستجد أن بعض المهام تتكرر في أكثر من مسار. قد تحتاج إلى التحقق من صلاحيات المستخدم، أو قياس زمن الاستجابة، أو السماح لواجهة أمامية موجودة على نطاق مختلف بإرسال الطلبات إلى الخادم.

بدلًا من تكرار هذه المهام داخل كل معالج، يتيح لك Barq استخدام **Middleware** لمشاركة السلوك بين المسارات، و**Route Groups** لتنظيم المسارات وتطبيق السلوك المناسب على مجموعات محددة منها.

## ما هي Middleware؟

الـ `Middleware` هي طبقة منطقية تنفّذ عملًا مشتركًا حول معالجة الطلب. على سبيل المثال، يمكن استخدامها لتسجيل معلومات الطلب، أو التحقق من وجود بيانات المصادقة، أو إضافة ترويسات إلى الاستجابة.

يدعم Barq في هذا النمط خطافين أساسيين:

- `before`: لتنفيذ المنطق قبل المعالج النهائي للمسار.
- `after`: لمعالجة الاستجابة بعد تنفيذ المعالج النهائي.

تساعدك هذه الخطافات على فصل المهام المشتركة عن منطق المسار نفسه، مما يجعل الكود أسهل في القراءة والصيانة.

## بنية Middleware

يمكنك تعريف Middleware على هيئة كائن يحتوي على `before` أو `after` أو كليهما:

```ts
import type { Middleware } from "@barqel/barq";

export const requestTimer: Middleware = {
  before(ctx) {
    ctx.state.startTime = performance.now();
  },

  after(ctx, response) {
    const duration = (
      performance.now() - (ctx.state.startTime as number)
    ).toFixed(2);

    const headers = new Headers(response.headers);
    headers.set("X-Response-Time", `${duration}ms`);

    return new Response(response.body, {
      ...response,
      headers,
    });
  },
};
```

### كيف يعمل المثال؟

**1. تسجيل وقت بداية الطلب**

```ts
before(ctx) {
  ctx.state.startTime = performance.now();
}
```

يستخدم الخطاف `performance.now()` لتسجيل وقت بداية المعالجة، ثم يحفظ القيمة في `ctx.state` حتى يمكن الوصول إليها لاحقًا.

**2. حساب مدة المعالجة**

```ts
const duration = (
  performance.now() - (ctx.state.startTime as number)
).toFixed(2);
```

يحسب الكود الفرق بين الوقت الحالي ووقت البداية. وتحوّل `toFixed(2)` النتيجة إلى قيمة تحتوي على منزلتين عشريتين.

**3. إضافة ترويسة إلى الاستجابة**

```ts
const headers = new Headers(response.headers);
headers.set("X-Response-Time", `${duration}ms`);
```

ينشئ الكود مجموعة ترويسات من ترويسات الاستجابة الحالية، ثم يضيف `X-Response-Time` لعرض المدة المحسوبة.

**4. إرجاع الاستجابة بالترويسات الجديدة**

```ts
return new Response(response.body, {
  ...response,
  headers,
});
```

يعيد الخطاف استجابة تحتوي على الجسم الأصلي والترويسات المحدّثة.

بعد تسجيل هذه الـ Middleware على التطبيق، يمكنك استخدام مدة الاستجابة في أدوات المطور أو مراقبة الطلبات دون تكرار منطق القياس في كل مسار.

> **ملاحظة:** يقيس هذا المثال الزمن بين تنفيذ خطافي `before` و`after` وفق مسار التنفيذ الفعلي. لا تفترض أنه يمثل زمن الشبكة الكامل بين العميل والخادم.

## مشاركة الحالة المكتوبة الأنواع (Typed State)

قد تحتاج Middleware إلى استخراج بيانات ثم إتاحتها لمعالج المسار. على سبيل المثال، يمكن لطبقة المصادقة التحقق من بيانات الاعتماد وإتاحة معلومات المستخدم للمسارات اللاحقة.

يدعم Barq إرجاع كائن من `before` ودمجه تلقائيًا في `ctx.state`، مع إمكانية استنتاج الأنواع في TypeScript.

```ts
import { App, json } from "@barqel/barq";

const authMiddleware = {
  before(ctx) {
    const token = ctx.req.headers.get("Authorization");

    if (!token) {
      return new Response("Unauthorized", {
        status: 401,
      });
    }

    return {
      user: {
        id: "user_123",
        role: "admin",
      },
    };
  },
};

const app = new App()
  .use(authMiddleware)
  .get("/profile", (ctx) => {
    return json({
      user: ctx.state.user,
    });
  });
```

### ما الذي يحدث هنا؟

1. تقرأ Middleware ترويسة `Authorization` من الطلب.
2. إذا لم تكن الترويسة موجودة، تعيد استجابة `401 Unauthorized`.
3. إذا كانت موجودة، تعيد كائنًا يحتوي على بيانات المستخدم.
4. يدمج Barq الكائن المعاد في `ctx.state`، بحيث يستطيع معالج `/profile` الوصول إلى `ctx.state.user`.

وبفضل استنتاج الأنواع، يستطيع TypeScript معرفة شكل `ctx.state.user` من الكائن الذي تعيده Middleware، بدلًا من اضطرارك إلى تعريف النوع يدويًا في كل مسار.

### لماذا تفيدك Typed State؟

تساعدك هذه الآلية على مشاركة البيانات التي تحتاجها المسارات، مثل معلومات المستخدم أو بيانات جرى استخراجها أثناء معالجة الطلب.

كما تجعل الكود أوضح؛ فبدلًا من إعادة تنفيذ الخطوات نفسها في كل معالج، تنفّذ Middleware المهمة مرة واحدة وتتيح نتيجتها عبر `ctx.state`.

**تنبيه أمني:** المثال يوضح طريقة مشاركة الحالة، وليس نظام مصادقة مكتملًا. وجود ترويسة `Authorization` وحده لا يثبت صحة هوية المستخدم. في التطبيق الحقيقي، تحقّق من بيانات الاعتماد قبل إنشاء كائن المستخدم، ولا تمنح صلاحيات إدارية لمجرد وجود الترويسة.

كذلك، إذا أعادت Middleware استجابة مباشرة مثل `401`، فلن يكون من المنطقي متابعة المعالجة باعتبار الطلب مصادقًا عليه.

## إعداد CORS المدمج

إذا كانت واجهة التطبيق الأمامية تعمل على نطاق مختلف عن نطاق الخادم، فقد يحتاج المتصفح إلى السماح بالطلب وفق سياسة مشاركة الموارد بين المصادر المختلفة، المعروفة باسم **CORS**.

يوفر Barq الدالة `cors()` لإعداد هذه السياسة دون الحاجة إلى حزمة خارجية إضافية.

```ts
import { App, cors } from "@barqel/barq";

const app = new App();

app.use(
  cors({
    origin: [
      "https://myfrontend.com",
      "https://app.myfrontend.com",
    ],
    methods: ["GET", "POST", "PUT", "DELETE"],
    allowedHeaders: ["Content-Type", "Authorization"],
    credentials: true,
    maxAge: 86400,
  }),
);
```

### شرح الخيارات

- `origin`: النطاقات المسموح لها بإجراء الطلبات من المتصفح. يحدد المثال نطاقين مسموحًا بهما.
- `methods`: طرق HTTP المسموح بها، مثل `GET` و`POST` و`PUT` و`DELETE`.
- `allowedHeaders`: الترويسات التي يُسمح للطلب باستخدامها، مثل `Content-Type` و`Authorization`.
- `credentials`: يحدد ما إذا كان إعداد CORS يسمح بطلبات بيانات الاعتماد، وفق سلوك التنفيذ.
- `maxAge`: مدة التخزين المؤقت لنتيجة طلبات الفحص المسبق، بالثواني؛ القيمة `86400` تعادل يومًا واحدًا.

### ما هو طلب Preflight؟

قبل بعض طلبات المتصفح، قد يرسل المتصفح طلبًا تمهيديًا باستخدام طريقة `OPTIONS` ليتحقق من أن الخادم يسمح بالمصدر والطريقة والترويسات المطلوبة. يسمى هذا الطلب **Preflight**.

يتعامل `cors()` في Barq تلقائيًا مع طلبات Preflight، ويعيد استجابة `204 No Content` مع ترويسات CORS المناسبة.

هذا يقلل الحاجة إلى كتابة معالجة منفصلة لطلبات `OPTIONS` التي تنشأ بسبب سياسة CORS.

### تنبيهات مهمة عند إعداد CORS

- أضف النطاقات التي تثق بها فقط، ولا تسمح لأي نطاق لمجرد تسهيل التطوير.
- إذا كنت تستخدم `credentials: true`، فتحقق من أن إعداد `origin` متوافق مع متطلبات CORS الخاصة بطلبات بيانات الاعتماد؛ فلا يجوز استخدام `*` بدلًا من مصدر محدد في هذه الحالة.
- CORS ليس بديلًا عن المصادقة أو التحقق من الصلاحيات. إنه يتحكم في كيفية تعامل المتصفحات مع الطلبات بين المصادر، ولا يمنع جميع أنواع العملاء من إرسال الطلبات إلى الخادم.

## مجموعات المسارات (Route Groups)

عندما يحتوي التطبيق على عدد كبير من المسارات، يصبح من المفيد جمع المسارات المرتبطة ضمن بادئة واحدة، وتطبيق Middleware مشتركة عليها.

تتيح لك `app.group()` إنشاء مجموعة من المسارات تحت بادئة محددة، مع إمكانية إضافة Middleware للمجموعة أو لمجموعة متداخلة داخلها.

```ts
app.group("/api/v1", requireApiKey, (v1) => {
  v1.get("/users", listUsers);

  v1.group("/admin", requireAdmin, (admin) => {
    admin.get("/metrics", getMetrics);
  });
});
```

### كيف تُبنى عناوين المسارات؟

في هذا المثال:

- المجموعة الخارجية لها البادئة `/api/v1`.
- المسار `v1.get("/users", listUsers)` يصبح عنوانه `/api/v1/users`.
- المجموعة الداخلية لها البادئة `/admin` ضمن المجموعة الخارجية.
- المسار `admin.get("/metrics", getMetrics)` يصبح عنوانه `/api/v1/admin/metrics`.

تساعدك البادئات على تنظيم واجهة API دون الحاجة إلى تكرار الجزء المشترك من العنوان في كل مسار.

### تطبيق Middleware على المجموعات

في المثال السابق، تمر المجموعة الخارجية عبر `requireApiKey`، بينما تُضاف `requireAdmin` إلى المجموعة الداخلية.

يتيح لك هذا تنظيم متطلبات الوصول بحسب نوع المسار:

- مسارات API التي تتطلب مفتاحًا صالحًا.
- مسارات إدارية تحتاج إلى تحقق إضافي من الصلاحيات.

احرص على أن تنفّذ كل Middleware التحقق الفعلي المطلوب، وألا تكتفي بوجود بيانات اعتماد دون التحقق من صحتها وصلاحياتها.

## كيف تختار الأداة المناسبة؟

- استخدم **Middleware** عندما تريد مشاركة سلوك بين عدة مسارات، مثل القياس أو المصادقة أو تعديل الاستجابة.
- استخدم **Typed State** عندما تحتاج إلى تمرير بيانات محسوبة إلى معالج المسار مع الاستفادة من استنتاج أنواع TypeScript.
- استخدم **`cors()`** عندما تحتاج إلى تحديد المصادر والطرق والترويسات المسموح بها لطلبات المتصفح.
- استخدم **Route Groups** عندما تريد تنظيم المسارات تحت بادئة مشتركة وتطبيق Middleware على مجموعة كاملة.

يمكنك الجمع بين هذه الأدوات لبناء تطبيق منظم: تضع السلوك المشترك في Middleware، وتشارك البيانات عبر `ctx.state`، وتضبط CORS عند الحاجة، ثم تجمع المسارات المرتبطة ضمن مجموعات واضحة.
