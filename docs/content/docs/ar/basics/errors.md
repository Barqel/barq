تحدث الأخطاء في كل تطبيق: قد لا يجد المستخدم المورد الذي يطلبه، أو قد يرسل طلبًا غير صالح، أو قد يحدث خلل غير متوقع أثناء معالجة الطلب.

يوفّر Barq طريقتين للتعامل مع هذه الحالات: **إرجاع خطأ HTTP مقصود** باستخدام `HttpError`، أو **تخصيص طريقة معالجة الأخطاء** على مستوى التطبيق. ويمكنك أيضًا تحديد الاستجابة التي يتلقاها العميل عندما يطلب مسارًا غير موجود.

## أخطاء HTTP المتوقعة

استخدم `HttpError` عندما تعرف أن الطلب لا يمكن إكماله وتريد إرجاع حالة HTTP محددة، مثل `400 Bad Request` أو `404 Not Found`.

لنفترض أن لديك مسارًا يعرض طلبًا تجاريًا باستخدام معرّفه:

```ts
import { HttpError } from "@barqel/barq";

app.get("/orders/:id", (ctx) => {
  const order = findOrder(ctx.params.id);

  if (!order) {
    throw new HttpError(404, {
      error: "Order not found",
    });
  }

  return json(order);
});
```

في هذا المثال، يبحث التطبيق عن الطلب باستخدام `ctx.params.id`. إذا لم يعثر عليه، يرمي `HttpError` بالحالة `404` بدلًا من إرجاع استجابة نجاح لا تعبّر عن النتيجة الحقيقية.

أما إذا وُجد الطلب، فيعيد التطبيق بياناته كالمعتاد.

### كيف يعمل `HttpError`؟

يقبل المُنشئ ثلاثة معاملات:

```ts
new HttpError(status, body?, headers?)
```

- `status`: رمز حالة HTTP، ويجب أن يكون عددًا من `100` إلى `599`.
- `body`: جسم الاستجابة الذي تريد إرساله إلى العميل. إذا لم تحدده، ينشئ Barq كائن خطأ أساسيًا يناسب الحالة.
- `headers`: ترويسات HTTP الإضافية للاستجابة، عند الحاجة.

يحوّل معالج الأخطاء الافتراضي جسم الخطأ إلى JSON.

على سبيل المثال، يمكنك إرجاع خطأ `400` عندما تكون قيمة أحد المدخلات غير مقبولة:

```ts
app.get("/reports/:year", (ctx) => {
  const year = Number(ctx.params.year);

  if (!Number.isInteger(year) || year < 2000) {
    throw new HttpError(400, {
      error: "Invalid year",
      message: "Year must be an integer greater than or equal to 2000.",
    });
  }

  return json({ year });
});
```

هذا المثال يوضّح الفكرة: عندما يكون الخطأ متوقعًا ومعروف السبب، أعد حالة مناسبة وجسمًا يشرح المشكلة بدلًا من التعامل معه باعتباره عطلًا داخليًا في الخادم.

> **متى تستخدم `HttpError`؟**
>
> استخدمه عندما تعرف سبب رفض الطلب وتريد تحديد حالة HTTP بوضوح، مثل عدم وجود مورد أو إرسال قيمة غير صالحة. أما الأخطاء غير المتوقعة، مثل خلل برمجي أو فشل غير متوقع في عملية داخلية، فدع معالج الأخطاء يتعامل معها.

## تخصيص معالج الأخطاء

إذا أردت توحيد شكل الأخطاء في تطبيقك، يمكنك تسجيل معالج عام باستخدام `app.onError()`:

```ts
app.onError((error, ctx) => {
  if (error instanceof HttpError) {
    return json(
      {
        error: error.message,
        details: error.body,
      },
      error.status,
    );
  }

  console.error("Request failed:", error);

  return json(
    { error: "Internal Server Error" },
    500,
  );
});
```

يستقبل المعالج الخطأ وبيانات سياق الطلب، ثم يحدد الاستجابة المناسبة:

1. **إذا كان الخطأ من نوع `HttpError`:** يعيد حالة HTTP التي حددتها، مع معلومات الخطأ.
2. **إذا كان الخطأ غير متوقع:** يسجّله على الخادم، ثم يعيد استجابة عامة بحالة `500 Internal Server Error`.

بهذا يمكنك التحكم في طريقة عرض الأخطاء بدلًا من الاعتماد بالكامل على المعالجة الافتراضية.

### لماذا يجب إخفاء تفاصيل الأخطاء الداخلية؟

قد يحتوي الخطأ غير المتوقع على معلومات لا ينبغي كشفها للعميل، مثل تفاصيل الملفات أو مسارات الخادم أو بيانات داخلية تساعد على استغلال ثغرة.

لذلك، اتبع قاعدتين:

- سجّل تفاصيل الأخطاء غير المتوقعة على الخادم حتى تتمكن من تشخيصها.
- أرسل للعميل رسالة عامة لا تكشف تفاصيل التنفيذ أو الأسرار.

من دون معالج مخصص، يخفي Barq تفاصيل الأخطاء غير المتوقعة في بيئة الإنتاج. وفي بيئة التطوير، يمكن إظهار التفاصيل عند تفعيل `development: true` أو ضبط `NODE_ENV=development`.

**تنبيه:** إذا كتبت معالجًا مخصصًا، فأنت مسؤول عن الاستجابة التي يعيدها. احرص على عدم إضافة تفاصيل داخلية إلى استجابات الإنتاج دون قصد.

## تخصيص استجابة المسار غير الموجود

عندما يطلب العميل مسارًا لا يطابق أي مسار مسجّل في التطبيق، يمكنك تخصيص الاستجابة باستخدام `app.notFound()`:

```ts
app.notFound((ctx) => {
  return json(
    {
      error: "Not Found",
      path: ctx.pathname,
    },
    404,
  );
});
```

في هذا المثال، يعيد التطبيق حالة `404 Not Found` مع اسم المسار المطلوب. تساعد هذه المعلومات على فهم الطلب الذي لم يُعثر على مسار مناسب له، ويمكنك تغيير شكل الجسم ليتوافق مع تنسيق الأخطاء المستخدم في بقية التطبيق.

مثلًا، إذا طلب العميل `/orders/123/details` ولم يكن هناك مسار يطابق هذا العنوان، فسيستخدم Barq معالج `notFound` لإرجاع الاستجابة الاحتياطية.

### الفرق بين `404` و`405`

من المهم التمييز بين حالتين مختلفتين:

- **`404 Not Found`:** لا يوجد مسار يطابق الطلب.
- **`405 Method Not Allowed`:** المسار موجود، لكن طريقة HTTP المستخدمة غير مسموح بها لهذا المسار.

على سبيل المثال، إذا كان التطبيق يعرّف `GET /orders` فقط، فإن طلب `GET /orders` يطابق المسار، بينما طلب `POST /orders` يستخدم طريقة غير مدعومة. يعيد Barq في الحالة الثانية الرمز `405 Method Not Allowed` بدلًا من `404 Not Found`، لأن المسار موجود لكن الطريقة غير مسموح بها.

لذلك، لا تفترض أن كل طلب لم يحصل على الاستجابة المتوقعة سيصل إلى معالج `notFound`. فالمعالج مخصص للطلبات التي لا تطابق مسارًا.

## أفضل الممارسات

- استخدم `HttpError` للأخطاء المتوقعة التي تحتاج إلى حالة HTTP محددة.
- استخدم `app.onError()` لتوحيد معالجة الأخطاء وتسجيل الأعطال غير المتوقعة.
- استخدم `app.notFound()` لتقديم استجابة واضحة عندما لا يوجد مسار مطابق.
- اختر رموز HTTP التي تعبّر بدقة عن المشكلة، ولا تستخدم `500` لخطأ متوقع في مدخلات العميل.
- لا تكشف مكدس الاستدعاءات أو الأسرار أو تفاصيل الخادم في استجابات الإنتاج.
- اجعل شكل استجابات الأخطاء متناسقًا عبر التطبيق حتى يسهل على العملاء التعامل معها.

بهذا تفصل بين الأخطاء التي يتوقعها التطبيق، والأعطال التي تحتاج إلى تشخيص، والطلبات التي لا تجد مسارًا مناسبًا — مع إبقاء الاستجابات واضحة وآمنة.
