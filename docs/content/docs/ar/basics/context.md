# سياق الطلب (Request Context)

عندما يصل طلب HTTP إلى تطبيقك، يحتاج معالج المسار إلى معلومات عن هذا الطلب: ما عنوانه؟ وما قيم المعاملات الموجودة فيه؟ وكيف يقرأ البيانات التي أرسلها العميل؟ وهل توجد معلومات أضافتها الوسائط البرمجية أثناء معالجة الطلب؟

يوفر Barq كائنًا يسمى `Context`، ويُشار إليه غالبًا بالاختصار `ctx`، ليجمع هذه المعلومات والمساعدات في مكان واحد.

يحصل كل معالج مسار وكل وسيط برمجي (`middleware`) على سياق الطلب وفقًا لواجهة Barq. يمكنك من خلاله قراءة الطلب الأصلي، والوصول إلى معاملات المسار والاستعلام، وقراءة جسم الطلب، واستخدام بعض العمليات المرتبطة بدورة حياة الاتصال.

## 1. قراءة بيانات الطلب والرابط

يوفر `Context` مجموعة من الخصائص والمساعدات للوصول إلى معلومات الطلب. يوضح الجدول التالي وظيفة كل منها:

| العضو | الوصف |
| --- | --- |
| `ctx.req` | كائن `Request` القياسي من Fetch API، ويحتوي على معلومات الطلب مثل الطريقة والترويسات والرابط. |
| `ctx.params` | معاملات المسار المستخرجة من نمط المسار، وهي مخصصة للقراءة. |
| `ctx.url` | نص رابط الطلب. |
| `ctx.pathname` | مسار الرابط دون سلسلة الاستعلام. |
| `ctx.query` | كائن `URLSearchParams` الذي يتيح قراءة معاملات الاستعلام والتعامل معها. |
| `ctx.queryParam(name)` | يعيد أول قيمة لمعامل الاستعلام المحدد، أو `null` إذا لم يوجد. |
| `ctx.queryParamAll(name)` | يعيد جميع القيم لمعامل استعلام قد يتكرر أكثر من مرة. |
| `ctx.state` | مساحة لحفظ حالة مرتبطة بالطلب، يمكن أن تملأها الوسائط البرمجية أو أجزاء التطبيق. |
| `ctx.development` | يوضح ما إذا كان Barq مضبوطًا على إظهار تفاصيل التطوير. |
| `ctx.ip` | عنوان IP للعميل بعد تطبيق سياسة الثقة بالوكيل. |

### مثال: قراءة الرابط ومعاملاته

لنفترض أن لديك المسار التالي:

```ts
app.get("/products/:id", (ctx) => {
  return json({
    id: ctx.params.id,
    pathname: ctx.pathname,
    sort: ctx.queryParam("sort"),
  });
});
```

وعندما يرسل العميل طلبًا إلى:

```text
/products/42?sort=price
```

يقرأ المعالج البيانات التالية:

- `ctx.params.id` — قيمة المعرّف في المسار، وهي `"42"`.
- `ctx.pathname` — المسار `/products/42` دون سلسلة الاستعلام.
- `ctx.queryParam("sort")` — قيمة معامل الاستعلام `sort`، وهي `"price"`.

هذا المثال يوضح قراءة القيم فقط؛ فلا يبحث عن المنتج في قاعدة بيانات ولا يتحقق من وجوده.

### معاملات الاستعلام قد تتكرر

يمكن أن يحتوي عنوان URL على أكثر من قيمة للاسم نفسه:

```text
/products?tag=books&tag=technology
```

إذا كنت تحتاج إلى أول قيمة فقط، استخدم:

```ts
const tag = ctx.queryParam("tag");
```

أما إذا كنت تحتاج إلى جميع القيم، فاستخدم:

```ts
const tags = ctx.queryParamAll("tag");
```

في المثال السابق، تمثل `tags` جميع القيم المرتبطة بالاسم `tag` وفقًا لترتيبها في عنوان الطلب.

انتبه إلى أن معاملات الاستعلام **نصوص وليست أنواع بيانات جاهزة**. إذا كان أحد المعاملات يمثل رقمًا أو قيمة من مجموعة محددة، فتحقق منه وحوّله قبل استخدامه في منطق التطبيق.

### الفرق بين `ctx.query` و`ctx.queryParam()`

`ctx.query` هو كائن `URLSearchParams` قياسي، بينما `ctx.queryParam(name)` مساعد مباشر لقراءة قيمة واحدة.

يمكنك استخدام `ctx.query` عندما تحتاج إلى الاستفادة من واجهة المتصفح القياسية، مثل التكرار على المعاملات أو فحص وجود اسم معين:

```ts
const query = ctx.query;

const hasSort = query.has("sort");
const sort = query.get("sort");
```

وبما أن `ctx.query` قابل للتغيير، فإن تعديل هذا الكائن يغيّر نسخة معاملات الاستعلام المستخدمة في سياق الطلب الحالي. لا تفترض أن هذا التعديل يغيّر عنوان الطلب الأصلي أو يؤثر في طلبات أخرى.

## 2. استخدام حالة الطلب (`ctx.state`)

تتيح `ctx.state` حفظ بيانات مرتبطة بالطلب الحالي، مثل معلومات يجهزها وسيط برمجي لتستخدمها معالجات المسارات لاحقًا.

من الأمثلة الشائعة:

- تخزين معلومات المستخدم بعد التحقق من هويته.
- الاحتفاظ بمعرّف تتبع للطلب.
- مشاركة نتيجة حسابها وسيط برمجي مع أكثر من معالج.

الفكرة الأساسية هي مشاركة بيانات تخص الطلب الجاري بدلًا من الاعتماد على متغير عام قد تتداخل قيمه بين الطلبات المتزامنة.

**مهم:** لا تخزن بيانات حساسة في الحالة إلا إذا كانت هناك حاجة واضحة لذلك، وتجنب الاحتفاظ بمعلومات الطلب في متغيرات عامة مشتركة بين جميع الطلبات.

## 3. قراءة جسم الطلب

قد يحتوي الطلب على بيانات أرسلها العميل، مثل كائن JSON أو نص أو نموذج أو ملف. يوفر `Context` مساعدات مختلفة لقراءة جسم الطلب بحسب التنسيق الذي تتوقعه.

```ts
const data = await ctx.json<unknown>();
const plainText = await ctx.text();
const form = await ctx.formData();
const fileLike = await ctx.blob();
const bytes = await ctx.arrayBuffer();
const stream = ctx.bodyStream; // أو ctx.stream()
```

كل سطر يقرأ الجسم أو يتيح الوصول إليه بطريقة مختلفة:

| المساعد | الاستخدام |
| --- | --- |
| `ctx.json<unknown>()` | قراءة الجسم وتحليله بوصفه JSON. |
| `ctx.text()` | قراءة الجسم كنص. |
| `ctx.formData()` | قراءة بيانات النماذج، بما فيها الحقول والملفات عند إرسالها بهذا التنسيق. |
| `ctx.blob()` | قراءة الجسم ككائن `Blob`. |
| `ctx.arrayBuffer()` | قراءة الجسم كمصفوفة بايتات في `ArrayBuffer`. |
| `ctx.bodyStream` أو `ctx.stream()` | الوصول إلى الجسم كتدفق لمعالجة البيانات تدريجيًا. |

### مثال: قراءة JSON

```ts
app.post("/echo", async (ctx) => {
  const data = await ctx.json<unknown>();

  return json({ received: data });
});
```

يقرأ هذا المسار جسم الطلب، ثم يعيد البيانات التي استقبلها داخل الخاصية `received`.

استخدام `unknown` مقصود: فهو يمنع TypeScript من افتراض أن البيانات تطابق بنية معينة قبل التحقق منها.

### هل يكفي `ctx.json<T>()` للتحقق من البيانات؟

لا. تحديد النوع العام في `ctx.json<T>()` يساعد TypeScript على فهم النوع الذي تريد التعامل معه، لكنه **لا يتحقق من صحة البيانات الواردة أثناء التشغيل**.

قد يرسل العميل JSON صالحًا نحويًا، لكنه يفتقد حقلًا مطلوبًا أو يحتوي على قيمة غير مقبولة. لذلك، افحص بنية البيانات وقيمها قبل الاعتماد عليها.

استخدم `validateJson()` مع محلل مناسب لفحص البيانات من النوع `unknown`. لمعرفة الطريقة العملية، راجع [التحقق من JSON](/ar/docs/basics/validation).

### التخزين المؤقت وإعادة قراءة الجسم

تخزّن مساعدات قراءة الجسم البيانات المقروءة مؤقتًا، ولذلك يمكن طلب التمثيلات المخزنة أكثر من مرة وفقًا لسلوك Barq.

لكن التدفق مختلف: عند استهلاك جسم الطلب من خلال التدفق، لا يمكنك افتراض إمكانية قراءته مرة أخرى. لهذا السبب، اختر طريقة القراءة المناسبة قبل البدء بمعالجة الجسم، خاصة عند التعامل مع ملفات كبيرة أو بيانات تصل تدريجيًا.

## 4. إعادة التوجيه

يمكنك استخدام `ctx.redirect(url, status?)` لإعادة توجيه العميل إلى عنوان آخر.

تأخذ العملية عنوان الوجهة، ويمكن أن تأخذ رمز حالة HTTP اختياريًا. ويستخدم Barq إعداد `allowedRedirectHosts` في التطبيق للتحقق من روابط إعادة التوجيه المطلقة.

هذا التحقق مهم عندما تكون وجهة إعادة التوجيه مبنية على مدخلات المستخدم؛ فإعادة توجيه المستخدم إلى موقع خارجي غير موثوق قد تفتح المجال لهجمات إعادة التوجيه المفتوحة.

قبل استخدام إعادة التوجيه، تأكد من أن الوجهة مسموح بها، وأن إعدادات المضيفين المسموحين تتوافق مع احتياجات التطبيق.

للتعرف على أنواع الاستجابات وإعادة التوجيه، راجع [الاستجابات وإعادة التوجيه](/ar/docs/basics/responses).

## 5. التحكم في مهلة الطلب

توفر واجهة السياق عمليتين للتعامل مع مهلة الطلب عند توفر خادم Bun:

- `ctx.timeout(seconds)` — يضبط مهلة الطلب الحالي.
- `ctx.disableTimeout()` — يعطّل المهلة.

قد تحتاج إلى تعديل المهلة عندما تنفذ عملية تستغرق وقتًا أطول من المعتاد. لكن تعطيل المهلة ليس خيارًا مناسبًا لكل طلب؛ فقد يؤدي إلى بقاء الاتصالات مفتوحة مدة طويلة إذا لم تنتهِ العملية كما هو متوقع.

استخدم `ctx.disableTimeout()` فقط عندما تتطلب العملية ذلك فعلًا، مثل بعض حالات التدفق طويل المدة، مع توفير طريقة واضحة لإنهاء الاتصال والتعامل مع الأخطاء.

## 6. قراءة عنوان IP للعميل

توفر `ctx.ip` عنوان IP للعميل بعد تطبيق سياسة الثقة بالوكيل.

تكتسب هذه النقطة أهمية عند تشغيل التطبيق خلف وكيل عكسي أو موازن أحمال، حيث قد يكون عنوان الاتصال المباشر هو عنوان الوكيل بدلًا من عنوان العميل الأصلي.

لكن لا تثق تلقائيًا بأي ترويسة تحمل عنوان IP. تعتمد القيمة التي يمكن الوثوق بها على إعدادات الثقة بالوكيل وطريقة وصول الطلب إلى الخادم.

اضبط سياسة الثقة بما يتناسب مع البنية التحتية الفعلية؛ فالإعداد غير الصحيح قد يسمح للعميل بتقديم عنوان IP مضلل. ويجب ألا يكون عنوان IP وحده وسيلة المصادقة أو التفويض.

## 7. ترقية الاتصال إلى WebSocket

يطلب `ctx.upgrade(data?)` ترقية الاتصال إلى WebSocket عبر خادم Bun، ويعيد ما إذا كانت الترقية قد نجحت. لا يدعم محوّل HTTP في Node.js ترقية WebSocket.

لكن إذا كنت تريد إنشاء نقطة WebSocket كاملة، فمن الأفضل استخدام `app.ws()` لتسجيل المسار وتعريف معالجات دورة حياة الاتصال، مع تطبيق فحوص التخويل المناسبة قبل السماح بالاتصال.

تختلف دورة حياة WebSocket عن دورة حياة طلب HTTP العادي: بعد نجاح الترقية، يصبح الاتصال قناة اتصال مستمرة بدلًا من تبادل طلب واستجابة منفرد.

لذلك، لا تستخدم `ctx.upgrade()` باعتباره بديلًا كاملًا عن إعداد مسار WebSocket وإدارة أحداثه.

## الخلاصة

يمنحك `Context` نقطة وصول موحدة إلى بيانات الطلب والأدوات المرتبطة بمعالجته. استخدم:

- `ctx.params` و`ctx.queryParam()` لقراءة معاملات الرابط.
- `ctx.req` للوصول إلى كائن الطلب القياسي.
- مساعدات الجسم لقراءة JSON والنصوص والنماذج والبيانات الثنائية.
- `ctx.state` لمشاركة البيانات المرتبطة بالطلب.
- `ctx.redirect()` وعمليات المهلة عند الحاجة.
- `ctx.ip` مع إعداد موثوق للوكيل.
- `app.ws()` عند بناء نقاط WebSocket ذات دورة حياة مستقلة.

اختر المساعد المناسب لكل مهمة، وتحقق من البيانات غير الموثوقة أثناء التشغيل، ولا تفترض أن قراءة البيانات أو تحديد نوعها في TypeScript يعني أنها صالحة للاستخدام.
