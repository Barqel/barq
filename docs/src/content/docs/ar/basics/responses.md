كل طلب HTTP ينتهي باستجابة يرسلها الخادم إلى العميل. قد تكون هذه الاستجابة بيانات JSON، أو نصًا عاديًا، أو استجابة بلا جسم، أو إعادة توجيه إلى عنوان آخر.

يوفر Barq مساعدات بسيطة لبناء هذه الاستجابات، كما يتيح لك استخدام كائن `Response` القياسي عندما تحتاج إلى تحكم أكبر في تفاصيل الاستجابة.

## أنواع الاستجابات

يمكن لمعالج المسار إرجاع كائن `Response` قياسي، أو استخدام قيمة يحولها Barq إلى استجابة HTTP.

على سبيل المثال، يمكن أن يعيد المسار بيانات مستخدم بصيغة JSON، أو رسالة نصية، أو استجابة تشير إلى نجاح إنشاء مورد جديد.

اختيار نوع الاستجابة المناسب يجعل واجهة API أوضح، ويساعد العميل على فهم نتيجة الطلب والتعامل معها بصورة صحيحة.

## استجابات JSON والنص والاستجابات الفارغة

يوفر Barq ثلاث مساعدات أساسية لإنشاء الاستجابات الشائعة:

- `json()` لإرجاع البيانات بصيغة JSON.
- `text()` لإرجاع نص عادي.
- `empty()` لإرجاع استجابة بلا جسم.

```ts
import { empty, json, text } from "@barqel/barq";

// بيانات بصيغة JSON.
return json({ id: "u-42" });

// JSON مع حالة تدل على إنشاء مورد.
return json({ created: true }, 201);

// JSON مع حالة خطأ.
return json({ error: "Not found" }, { status: 404 });

// نص عادي مع حالة HTTP.
return text("Accepted", 202);

// استجابة بلا جسم، وحالتها الافتراضية 204.
return empty();
```

الأمثلة السابقة بدائل مختلفة داخل معالجات المسارات؛ لا تضع جميع عبارات `return` في معالج واحد إذا كنت تتوقع تنفيذها جميعًا، لأن أول `return` يُنفّذ ينهي المعالج.

### 1. إرجاع JSON باستخدام `json()`

تُستخدم `json()` عندما تريد إرسال كائن أو مصفوفة أو قيمة مناسبة لتمثيل JSON.

```ts
app.get("/users/:id", (ctx) => {
  return json({
    id: ctx.params.id,
    name: "Mona",
  });
});
```

قد تكون الاستجابة مثل:

```json
{
  "id": "42",
  "name": "Mona"
}
```

يأخذ المثال معرّف المستخدم من المسار، ثم يعيد بياناته بصيغة JSON.

يضبط `json()` ترويسة `Content-Type` افتراضيًا على:

`application/json; charset=utf-8`

ويمكنك تحديد نوع محتوى آخر من خلال إعدادات الاستجابة التي تدعمها الدالة.

يمكن أيضًا تحديد حالة HTTP، بحسب الصيغة المستخدمة:

```ts
// تمرير الحالة مباشرة.
return json({ created: true }, 201);

// تمرير إعدادات الاستجابة.
return json(
  { error: "Not found" },
  { status: 404 },
);
```

استخدم `201 Created` عندما تكون العملية قد أنشأت موردًا جديدًا بالفعل، و`404 Not Found` عندما لا يوجد المورد المطلوب. اختيار الحالة الصحيحة يجعل استجاباتك أكثر وضوحًا للعملاء وأدوات المراقبة.

### 2. إرجاع نص باستخدام `text()`

إذا كانت الاستجابة رسالة نصية بسيطة، فلا حاجة إلى تحويلها إلى JSON:

```ts
app.get("/status", () => {
  return text("Service is running");
});
```

يمكنك أيضًا تحديد حالة HTTP:

```ts
return text("Accepted", 202);
```

تضبط `text()` نوع المحتوى على `text/plain; charset=utf-8` عند استخدام قيمة الحالة أو إعدادات الاستجابة وفق الواجهة الموضحة في Barq.

اختر `text()` عندما يكون النص نفسه هو النتيجة المطلوبة، مثل رسالة قصيرة أو محتوى نصي بسيط. أما إذا كنت تريد إرسال حقول متعددة، مثل رمز النتيجة ورسالتها وبيانات إضافية، فعادةً ما يكون JSON أنسب.

### 3. إرجاع استجابة فارغة باستخدام `empty()`

في بعض الحالات، لا تحتاج إلى إرسال جسم في الاستجابة. يوفر Barq الدالة:

```ts
empty(status?, headers?)
```

مثال:

```ts
app.post("/jobs/:id/cancel", (ctx) => {
  cancelJob(ctx.params.id);

  return empty();
});
```

تعيد `empty()` استجابة بلا جسم، وحالتها الافتراضية `204 No Content`.

تعني الحالة `204` أن الخادم أكمل العملية بنجاح، ولا يرسل محتوى في جسم الاستجابة.

يمكنك أيضًا تحديد الحالة والترويسات:

```ts
return empty(204, {
  "X-Operation": "completed",
});
```

استخدم استجابة فارغة عندما لا يحتاج العميل إلى بيانات إضافية بعد تنفيذ العملية. وإذا كنت بحاجة إلى إرجاع رسالة أو نتيجة أو تفاصيل عن المورد الذي أنشأته، فاستخدم `json()` أو `text()` بدلًا منها.

**مهم:** توجد حالات HTTP لا تسمح بإرسال جسم، حتى لو حاولت إنشاء استجابة تحتوي عليه. يتعامل Barq مع هذه الحالات بإرسال الاستجابة دون جسم.

## متى تستخدم `Response` القياسي؟

تغطي المساعدات `json()` و`text()` و`empty()` معظم الحالات الشائعة. لكنك قد تحتاج أحيانًا إلى التحكم المباشر في الاستجابة، مثل تحديد ترويسات متعددة أو إرجاع جسم متدفق.

في هذه الحالات، يمكنك إنشاء كائن `Response` قياسي وإرجاعه من معالج المسار:

```ts
app.get("/custom-response", () => {
  return new Response("Custom response", {
    status: 200,
    headers: {
      "Content-Type": "text/plain; charset=utf-8",
      "X-App-Version": "1.0.0",
    },
  });
});
```

يوضح المثال كيفية تحديد الحالة والترويسات مباشرة عند إنشاء الاستجابة.

من مزايا استخدام `Response` القياسي أنه يمنحك تحكمًا مباشرًا في واجهة الاستجابة. وهو مناسب عندما تحتاج إلى خصائص لا تغطيها المساعدات المختصرة، بما في ذلك بعض حالات التدفق.

لا تستخدمه لمجرد أنه أكثر تفصيلًا؛ فالمساعدات تجعل الكود أقصر وأسهل قراءة عندما تكون كافية.

## إعادة التوجيه (Redirects)

إعادة التوجيه هي استجابة تخبر العميل أن ينتقل إلى عنوان آخر. تُستخدم، على سبيل المثال، عندما تنتقل صفحة إلى عنوان جديد أو عندما تريد توجيه المستخدم إلى صفحة أخرى بعد إتمام عملية.

يدعم Barq الدالتين:

```ts
redirect(url, status?)
ctx.redirect(url, status?)
```

تقبل الدالتان حالات إعادة التوجيه التالية:

- `301 Moved Permanently`: يشير إلى انتقال دائم.
- `302 Found`: يشير إلى إعادة توجيه مؤقتة.
- `303 See Other`: يوجّه العميل إلى مورد آخر، ويُستخدم عادةً لتوجيهه إلى صفحة نتيجة بعد إرسال نموذج.
- `307 Temporary Redirect`: إعادة توجيه مؤقتة تحافظ على طريقة الطلب.
- `308 Permanent Redirect`: إعادة توجيه دائمة تحافظ على طريقة الطلب.

### مثال على إعادة التوجيه

```ts
app.get("/old-docs", (ctx) => {
  return ctx.redirect(
    "https://docs.example.com",
    302,
  );
});
```

يعيد هذا المسار استجابة إعادة توجيه مؤقتة إلى موقع التوثيق.

تساعدك `ctx.redirect()` على تنفيذ إعادة التوجيه من داخل معالج المسار، بينما تتيح الدالة المستقلة `redirect()` إنشاء استجابة إعادة توجيه دون الاعتماد على سياق الطلب.

اختر الحالة وفق معنى العملية، لا لمجرد أن جميع حالات إعادة التوجيه تبدو متشابهة. فالاختلاف بين الحفاظ على طريقة الطلب أو تغييرها قد يكون مهمًا، خاصةً عند إعادة توجيه طلبات `POST`.

## التحقق من وجهة إعادة التوجيه

إعادة التوجيه إلى عنوان يحدده المستخدم دون تحقق قد تؤدي إلى ثغرة تُعرف باسم **Open Redirect**. فقد يستغلها مهاجم لجعل التطبيق يرسل المستخدم إلى موقع خارجي مضلل.

لذلك يقيّد Barq أشكال الوجهات المقبولة. يجب أن تكون الوجهة أحد الشكلين التاليين:

- مسار يبدأ من الجذر، مثل `/account`.
- رابط HTTP أو HTTPS مطلق، مثل `https://docs.example.com`.

أما الروابط النسبية للبروتوكول، مثل `//host/path`، والروابط التي تحتوي على شرطات عكسية أو محارف تحكم، فيرفضها Barq.

### تحديد المضيفين المسموح بهم

إذا كان التطبيق يحتاج إلى إعادة التوجيه إلى نطاقات خارجية محددة، يمكنك إعداد قائمة بالمضيفين المسموح بهم عند إنشاء التطبيق:

```ts
const app = new App({
  allowedRedirectHosts: ["docs.example.com"],
});
```

في هذا المثال، تحدد قائمة السماح المضيف الخارجي الذي يمكن أن تستخدمه إعادة التوجيه عبر `ctx.redirect()`.

تفرض `ctx.redirect()` قائمة المضيفين المسموح بهم. أما الدالة المستقلة `redirect()` فتقبل معاملًا ثالثًا اختياريًا من النوع `ReadonlySet<string>` لتحديد قائمة المضيفين:

```ts
redirect(url, status?, allowedHosts?)
```

إذا لم تمرر قائمة إلى الدالة المستقلة، فإنها لا تقيّد المضيفين في روابط HTTP وHTTPS المطلقة.

**أفضل ممارسة:** لا تستخدم قيمة يرسلها المستخدم مباشرةً بوصفها وجهة إعادة توجيه. تحقّق من الوجهة، وفضّل المسارات الداخلية أو قائمة محددة من المضيفين الموثوق بهم.

## طلبات `HEAD`

تُستخدم طريقة HTTP `HEAD` لطلب البيانات الوصفية للاستجابة دون الحاجة إلى استلام جسمها. وهي تشبه `GET` من حيث الغرض، لكن العميل لا يحتاج إلى محتوى الاستجابة.

يزيل Barq أجسام استجابات `HEAD` مع الإبقاء على البيانات الوصفية للاستجابة.

إذا كنت بحاجة إلى سلوك مخصص لهذه الطريقة، يمكنك استخدام `head()` لتسجيل معالج خاص:

```ts
app.head("/status", () => {
  return empty();
});
```

هذا مثال توضيحي لمعالج `HEAD` يعيد استجابة بلا جسم. ويمكنك إرجاع ترويسات أو حالة مناسبة حسب احتياجات المسار.

### متى تحتاج إلى معالج `HEAD` مخصص؟

قد يكون من المفيد تعريف معالج مخصص عندما تريد التحكم في البيانات الوصفية التي يعيدها المسار، أو عندما تكون لديك متطلبات محددة لطريقة `HEAD`.

أما إذا كان سلوك Barq الافتراضي يحقق ما تحتاج إليه، فلا تضف معالجًا منفصلًا دون داعٍ.

تذكّر أن جسم استجابة `HEAD` لا يُرسل إلى العميل؛ لذلك لا تعتمد على قراءة جسم الاستجابة لمعرفة نتيجة الطلب.

## أفضل الممارسات

- استخدم `json()` لإرجاع البيانات المنظمة، و`text()` للمحتوى النصي، و`empty()` عندما لا تحتاج إلى جسم.
- اختر حالة HTTP تعبّر بدقة عن نتيجة العملية.
- استخدم `Response` القياسي عندما تحتاج إلى تحكم مباشر في الترويسات أو الجسم.
- اختر حالة إعادة التوجيه بناءً على كون الانتقال دائمًا أو مؤقتًا، وما إذا كان ينبغي الحفاظ على طريقة الطلب.
- تحقّق من وجهات إعادة التوجيه ولا تسمح بوجهات خارجية غير موثوقة.
- استخدم `HEAD` للحصول على البيانات الوصفية دون جسم الاستجابة.
- لا تفترض أن جميع أنواع الاستجابات تسمح بإرسال جسم؛ فبعض حالات HTTP تتطلب استجابة بلا جسم.

باختيار المساعد المناسب والحالة الصحيحة والتحقق من وجهات إعادة التوجيه، يمكنك بناء استجابات واضحة وآمنة يسهل على العملاء التعامل معها.
