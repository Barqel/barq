عندما يكبر التطبيق، يصبح تنظيم الكود مهمًّا بقدر أهمية كتابة الكود نفسه. فبدلًا من وضع جميع المسارات والمصادقة والمراقبة وإعدادات النظام في ملف واحد، يمكنك تقسيم التطبيق إلى وحدات مستقلة، تتولى كل وحدة منها مسؤولية واضحة.

يوفر Barq لهذا الغرض نظام إضافات يعتمد على **التركيب الوظيفي (Functional Composition)**، من خلال `app.plugin()` و`group.plugin()`.

الفكرة بسيطة: تكتب دالة تجمع المسارات والبرمجيات الوسيطة والإعدادات المرتبطة بميزة معينة، ثم تستخدمها لتركيب هذه الميزة داخل التطبيق أو داخل مجموعة محددة من المسارات.

لا يفرض هذا النمط عليك نظامًا معقدًا من الأصناف أو الحاويات أو طبقات التجريد. بل يتيح لك تنظيم التطبيق باستخدام دوال TypeScript واضحة، مع الحفاظ على فصل المسؤوليات وإمكانية إعادة استخدام الكود.

## ما هي الإضافة في Barq؟

الإضافة (Plugin) هي دالة تُستخدم لتسجيل أجزاء من التطبيق وتجميعها في وحدة وظيفية واحدة. يمكنها، بحسب الواجهات المتاحة، تسجيل المسارات أو ربط Middleware أو إنشاء مجموعات مسارات إضافية.

تُعرَّف الإضافة الأساسية بالشكل التالي:

```ts
type Plugin<TOptions = unknown> = (
  app: App,
  options?: TOptions,
) => void;
```

يتكون هذا التعريف من ثلاثة أجزاء:

- `app`: مرجع التطبيق الذي ستُسجَّل فيه المكونات.
- `options`: إعدادات اختيارية تتحكم في طريقة تركيب الإضافة.
- `void`: القيمة التي تعيدها دالة الإضافة نفسها؛ فهي لا تحتاج إلى إرجاع قيمة لكي تسجل المسارات.

### ماذا يحدث عند استدعاء `app.plugin()`؟

عند كتابة:

```ts
app.plugin(myPlugin, options);
```

تُستدعى دالة الإضافة أثناء تهيئة التطبيق، وتنفّذ عمليات التسجيل التي تحتوي عليها. ومن أمثلة ذلك:

- تسجيل مسارات جديدة.
- ربط Middleware.
- إنشاء مجموعات مسارات متداخلة.
- استخدام الإعدادات الممررة لتحديد المسارات أو السلوك الذي ستضيفه الوحدة.

بعد تركيب الإضافة، تصبح المسارات التي سجلتها جزءًا من التطبيق نفسه.

وتتيح واجهة `app.plugin()` أيضًا مواصلة استدعاءات التطبيق المتسلسلة (Fluent Chaining)، وفق واجهة Barq.

**النقطة المهمة:** الإضافة تنظّم كيفية بناء التطبيق، بينما يتعامل معالج المسار مع الطلب الفعلي عندما يصل إلى المسار المطابق.

## الإضافة مقابل Middleware ومعالج المسار

قد تبدو هذه المكونات متشابهة لأنها تشارك في بناء التطبيق، لكن لكل منها مسؤولية مختلفة.

| وجه المقارنة | Plugin | Middleware | Route Handler |
|---|---|---|---|
| متى تعمل؟ | أثناء تركيب التطبيق وتسجيل مكوناته | ضمن دورة معالجة الطلب، وفق موضعها في خط التنفيذ | عند معالجة طلب يطابق المسار |
| الوظيفة الأساسية | تجميع الميزات وتسجيل مكوناتها | تنفيذ سلوك مشترك حول معالجة الطلب | تنفيذ منطق المسار |
| تتعامل مع `Context`؟ | ليس بالضرورة؛ دالة الإضافة تستقبل التطبيق أو المجموعة | نعم، عبر سياق الطلب `ctx` | نعم، عبر سياق الطلب `ctx` |
| مثال شائع | وحدة للمستخدمين أو المراقبة | المصادقة أو قياس زمن الاستجابة | جلب مستخدم أو إنشاء طلب |

### لماذا لا تُعد الإضافة Middleware أخرى؟

انظر إلى الفرق في المثال التالي:

```ts
// تركيب ميزة داخل التطبيق.
app.plugin(healthPlugin, { version: "2.1.0" });
```

هذا الاستدعاء يسجّل مكونات الإضافة أثناء التهيئة.

أما Middleware، مثل تلك التي تتحقق من مفتاح وصول، فتنفّذ منطق التحقق ضمن معالجة الطلبات التي تمر بها.

وبالتالي، فإن مجرد تركيب الإضافة لا يعني تنفيذ منطقها الخاص بكل طلب. ومع ذلك، فإن أي Middleware أو معالج مسار تسجله الإضافة سيظل جزءًا من مسار التنفيذ عند معالجة الطلبات المطابقة.

من الأفضل تجنّب وصف تكلفة الإضافة بأنها «صفر نانوثانية» على نحو حرفي؛ فتركيب الإضافة نفسه له تكلفة أثناء التهيئة. المقصود أن استدعاء دالة الإضافة ليس خطوة تُضاف تلقائيًا إلى كل طلب بعد اكتمال التسجيل، ما لم تسجّل الإضافة مكونات تؤثر في معالجة الطلب.

## بناء أول إضافة: وحدة فحص حالة التطبيق

لنفترض أنك تريد توفير مسار يعرض حالة التطبيق وإصداره، ومسار آخر يعرض مدة تشغيل العملية عند الحاجة.

بدلًا من تسجيل هذه المسارات مباشرة في ملف التطبيق الرئيسي، يمكنك وضعها في إضافة مستقلة:

```ts
import { App, json } from "@barqel/barq";

interface HealthPluginOptions {
  version: string;
  uptime?: boolean;
}

export function healthPlugin(
  app: App,
  options?: HealthPluginOptions,
) {
  const version = options?.version ?? "1.0.0";

  app.get("/health", () =>
    json({
      status: "healthy",
      version,
    }),
  );

  if (options?.uptime) {
    app.get("/uptime", () =>
      json({
        uptime: process.uptime(),
      }),
    );
  }
}
```

ثم تركّب الإضافة داخل التطبيق:

```ts
import { App } from "@barqel/barq";
import { healthPlugin } from "./plugins/health";

const app = new App();

app.plugin(healthPlugin, {
  version: "2.1.0",
  uptime: true,
});
```

### شرح المثال

**1. تحديد خيارات الإضافة**

```ts
interface HealthPluginOptions {
  version: string;
  uptime?: boolean;
}
```

تحدد الواجهة أن `version` قيمة مطلوبة عند تمرير الخيارات، بينما `uptime` قيمة اختيارية. وبذلك يستطيع TypeScript اكتشاف الأخطاء في شكل الإعدادات قبل تشغيل التطبيق.

**2. توفير قيمة افتراضية**

```ts
const version = options?.version ?? "1.0.0";
```

يستخدم التعبير `?.` للوصول الآمن إلى الخيارات إذا كانت غير موجودة، ويستخدم `??` القيمة الافتراضية عندما تكون `version` غير محددة أو `null`.

**3. تسجيل مسار الحالة**

```ts
app.get("/health", () =>
  json({
    status: "healthy",
    version,
  }),
);
```

تسجل الإضافة مسارًا يعرض حالة التطبيق والإصدار الذي أُعدت به الوحدة.

**4. تسجيل مسار اختياري**

```ts
if (options?.uptime) {
  app.get("/uptime", () =>
    json({ uptime: process.uptime() }),
  );
}
```

لا يسجل التطبيق مسار `/uptime` إلا عندما تكون قيمة `uptime` صحيحة. هذا مثال على استخدام خيارات الإضافة لتحديد المكونات التي تُسجَّل أثناء التهيئة.

لاحظ أن `process.uptime()` يعرض مدة تشغيل عملية الخادم، وليس مدة تشغيل الإضافة أو مدة عمل طلب معين.

### متى يكون هذا التصميم مفيدًا؟

يفيد هذا الأسلوب عندما تريد أن تكون ميزة فحص الحالة قابلة للنقل بين التطبيقات. فبدلًا من نسخ المسارات إلى كل مشروع، تحتفظ بها في وحدة واحدة، ثم تركّبها بالإعدادات المناسبة.

ويمكن تطبيق النمط نفسه على وحدات المستخدمين والمنتجات والفواتير والمراقبة.

## إنشاء إضافة لمجموعة مسارات

ليست كل إضافة بحاجة إلى تسجيل مسارات على مستوى التطبيق بالكامل. أحيانًا تريد بناء وحدة تستهدف مجموعة محددة، مثل مجموعة واجهة المستخدمين البرمجية.

يمكنك كتابة دالة تستقبل `RouteGroup`:

```ts
import type { RouteGroup } from "@barqel/barq";
import { json } from "@barqel/barq";

export function usersCrudPlugin<
  P extends string,
  S extends object,
>(group: RouteGroup<P, S>) {
  group.get("/", () => json({ users: [] }));

  group.get("/:id", (ctx) =>
    json({ id: ctx.params.id }),
  );

  group.post("/", (ctx) =>
    json({ created: true }, 201),
  );
}
```

ثم تركّبها داخل مجموعة:

```ts
import { App } from "@barqel/barq";
import { usersCrudPlugin } from "./plugins/users";

const app = new App();

app.group("/api/v1/users", (usersApi) => {
  usersApi.plugin(usersCrudPlugin);
});
```

### لماذا تستقبل الإضافة `RouteGroup`؟

لأن هذه الوحدة لا تحتاج إلى امتلاك التطبيق بالكامل؛ يكفي أن تحصل على المجموعة التي ستضيف إليها المسارات.

في هذا المثال، المسارات المسجّلة نسبيًّا داخل المجموعة تصبح:

| المسار داخل المجموعة | المسار الناتج |
|---|---|
| `/` | `/api/v1/users` |
| `/:id` | `/api/v1/users/:id` |

وإذا كانت واجهة المجموعة تدعم إضافة المسارات بهذه الصورة، فإن المسار `POST /` يسجل أيضًا تحت بادئة المجموعة.

تتيح الأنواع العامة `P` و`S` للإضافة العمل مع مجموعات ذات معلومات نوعية مختلفة، وفق تعريف `RouteGroup` في Barq. ولا تحتاج إلى فهم تفاصيل الأنواع العامة لاستخدام النمط؛ يكفي أن تعرف أن الإضافة تستقبل المجموعة التي ستسجّل المسارات داخلها.

**متى تختار هذا الأسلوب؟**

استخدم إضافة المجموعة عندما تريد وحدة قابلة لإعادة الاستخدام تحت بادئات مختلفة، أو عندما تحتاج إلى إبقاء مسؤوليات ميزة محددة منفصلة عن بقية التطبيق.

## بناء وحدة متكاملة: Middleware ومسارات المراقبة

في التطبيقات الأكبر، قد لا تقتصر الوحدة على تسجيل المسارات. فقد تحتاج أيضًا إلى Middleware خاصة تحمي هذه المسارات.

لنفترض أنك تريد إنشاء وحدة للمراقبة الداخلية، بحيث لا يمكن الوصول إلى مساراتها من دون ترويسة مفتاح وصول.

```ts
import type { App, Middleware } from "@barqel/barq";
import { HttpError, json } from "@barqel/barq";

interface MetricsOptions {
  apiKeyHeader: string;
}

export function metricsModule(
  app: App,
  options?: MetricsOptions,
) {
  const headerName =
    options?.apiKeyHeader ?? "x-metrics-key";

  const enforceMetricsKey: Middleware = {
    before(ctx) {
      if (!ctx.req.headers.has(headerName)) {
        throw new HttpError(401, {
          error: "Missing Metrics Access Key",
        });
      }
    },
  };

  app.group(
    "/internal/metrics",
    enforceMetricsKey,
    (metrics) => {
      metrics.get("/system", () => {
        const memory = process.memoryUsage();

        return json({ memory });
      });
    },
  );
}
```

### ما الذي تجمعه هذه الوحدة؟

تجمع هذه الإضافة ثلاثة أجزاء في مكان واحد:

1. **الإعدادات:** تتيح تغيير اسم الترويسة المستخدمة لمفتاح الوصول.
2. **Middleware:** تتحقق من وجود الترويسة قبل متابعة معالجة الطلب.
3. **المسارات:** تسجّل مسارًا لعرض معلومات الذاكرة ضمن مجموعة المراقبة الداخلية.

عند تركيب الإضافة، لا تحتاج إلى تكرار تعريف Middleware أو بادئة المسارات في أماكن أخرى.

### تنبيه أمني مهم

هذا المثال يتحقق من **وجود الترويسة فقط**، ولا يتحقق من صحة المفتاح أو قيمته. لذلك فهو ليس نظام مصادقة مكتملًا، ولا ينبغي اعتباره حماية كافية لمسارات حساسة.

في التطبيق الحقيقي، قارن قيمة المفتاح بقيمة موثوقة محفوظة في إعدادات آمنة، أو استخدم آلية مصادقة مناسبة. كما يجب حماية بيانات المراقبة من الوصول غير المصرح به.

## الحدود الهندسية لنظام الإضافات

يعتمد نمط الإضافات هنا على تركيب المكونات أثناء تهيئة التطبيق، وليس على تحميل وحدات ديناميكيًا لكل طلب. ومن المهم فهم ما يعنيه ذلك عند تصميم الإضافات.

### 1. التركيب المتزامن

دالة الإضافة الموضحة في واجهة `Plugin` دالة متزامنة تعيد `void`. لذلك ينبغي أن تتم عمليات تسجيل المسارات والمكونات التي تعتمد عليها أثناء تركيب التطبيق.

لا تجعل دالة الإضافة `async` اعتمادًا على هذا التعريف وحده؛ فإرجاع `Promise` لا يتوافق مع نوع الإضافة المعروض هنا.

إذا كانت الوحدة تحتاج إلى تحميل إعدادات من ملف أو الاتصال بقاعدة بيانات قبل تسجيل مساراتها، فافصل خطوة التهيئة غير المتزامنة عن دالة التركيب المتزامنة، وتأكد من اكتمالها قبل تشغيل الخادم.

### 2. إدارة الموارد الخارجية

قد تحتاج بعض الوحدات إلى موارد لا تقتصر على تسجيل المسارات، مثل اتصالات قواعد البيانات أو المؤقتات أو الاتصالات الخارجية.

لا تفترض أن تسجيل الإضافة وحده يعني أن Barq سيدير دورة حياة هذه الموارد تلقائيًا. يجب أن تحدد آلية واضحة لتهيئتها وإغلاقها، بالاعتماد على واجهات دورة الحياة التي يوفرها إصدار Barq المستخدم.

وبوجه خاص، تحقّق من واجهة إيقاف الخادم الفعلية قبل الاعتماد على `app.stop()` لإغلاق الموارد؛ فإيقاف الخادم وإدارة تنظيف الموارد ليسا بالضرورة العملية نفسها.

### 3. لا يوجد عزل تلقائي بين الإضافات

الإضافة التي تسجّل مسارات أو Middleware في التطبيق تضيف هذه المكونات إلى التطبيق المشترك. لا ينبغي اعتبارها بيئة معزولة أو افتراض أن أخطاءها أو سلوكها محصور داخل ملفها.

لذلك:

- اجعل مسؤولية كل إضافة واضحة.
- تجنب تعارض المسارات بين الوحدات.
- تحقّق من الخيارات التي تستقبلها الإضافة.
- لا تمنح الإضافات غير الموثوقة صلاحية تعديل التطبيق.

## تنظيم مشروع باستخدام الإضافات

يمكنك استخدام بنية مجلدات تجعل مسؤولية كل وحدة واضحة، على سبيل المثال:

```text
src/
├── plugins/
│   ├── health.ts
│   ├── metrics.ts
│   └── users.ts
└── app.ts
```

في هذا التنظيم:

- `health.ts` مسؤول عن مسارات فحص الحالة.
- `metrics.ts` مسؤول عن مسارات المراقبة ومتطلبات الوصول إليها.
- `users.ts` مسؤول عن مسارات المستخدمين.
- `app.ts` هو المكان الذي تُركّب فيه الوحدات داخل التطبيق.

هذه مجرد بنية مقترحة وليست شرطًا يفرضه Barq. يمكنك تعديلها بحسب حجم المشروع وطبيعة وحداته.

## أفضل الممارسات

- اجعل كل إضافة مسؤولة عن ميزة محددة بدلًا من جمع وظائف غير مترابطة.
- مرّر الإعدادات إلى الإضافة بدلًا من توزيع القيم الثابتة داخل الكود.
- استخدم `group.plugin()` عندما تكون الوحدة مرتبطة بمجموعة مسارات، و`app.plugin()` عندما تحتاج إلى التركيب على مستوى التطبيق.
- افصل تهيئة الموارد غير المتزامنة عن تسجيل المسارات المتزامن.
- تحقّق من المصادقة والصلاحيات فعليًا؛ وجود الترويسة ليس دليلًا على صلاحية الوصول.
- اختبر الإضافة في تطبيق صغير قبل استخدامها في مشروع أكبر.
- لا تفترض أن الإضافات معزولة أو أن الموارد التي تنشئها ستُغلق تلقائيًا.

## الخلاصة

نظام الإضافات في Barq وسيلة لتنظيم التطبيق عن طريق **تركيب وحدات وظيفية صغيرة وواضحة**. استخدم الإضافة لتجميع المسارات والبرمجيات الوسيطة والإعدادات المرتبطة بميزة واحدة، واستخدم `app.plugin()` أو `group.plugin()` لتركيبها في المكان المناسب.

بهذا تستطيع تقسيم التطبيق إلى وحدات يسهل فهمها واختبارها وإعادة استخدامها، دون تحويل بنية المشروع إلى نظام تجريدي معقد.
