يوفر Barq أدوات لبناء تطبيقات HTTP وWebSocket، لكن **أمان التطبيق مسؤولية مشتركة بين الإطار والتطبيق وبيئة النشر**. فالإطار لا يستطيع وحده تحديد الوكلاء الموثوقين، أو حماية الأسرار، أو اختيار حدود الموارد المناسبة لكل خدمة.

يوضح هذا الدليل أهم الإعدادات والممارسات التي ينبغي مراجعتها قبل تشغيل تطبيق Barq في بيئة الإنتاج.

## لا تثق إلا بالوكلاء المعروفين

قد يعمل تطبيق Barq خلف وكيل عكسي (Reverse Proxy) مثل Nginx، أو خلف موازن تحميل. في هذه الحالة، قد يضيف الوكيل ترويسات مثل `X-Forwarded-For` لتوضيح عنوان IP الأصلي للعميل.

لكن هذه الترويسات ليست موثوقة تلقائيًا؛ إذ يمكن للعميل إرسال ترويسات مزيفة إذا لم تضبط الثقة بصورة صحيحة.

يتجاهل Barq ترويسات التحويل افتراضيًا، ويستخدم عنوان IP الذي يراه Bun للاتصال المباشر. إذا كنت تستخدم وكيلًا عكسيًا، فحدّد الوكلاء الذين تثق بهم صراحةً:

```ts
import { App } from "@barqel/barq";

const app = new App({
  trustProxy: ["127.0.0.1", "::1", "10.20.0.0/16"],
});
```

في هذا المثال، تتضمن قائمة الثقة عنواني الاسترجاع المحليين ونطاقًا شبكيًا داخليًا. **استخدم العناوين والنطاقات الفعلية لوكلائك فقط**؛ فالقيم هنا توضيحية وليست إعدادًا مناسبًا لكل بيئة.

### كيف تعمل الثقة في الوكيل؟

عند تفعيل `trustProxy`، يفحص Barq ترويسة `X-Forwarded-For` من أقرب قفزة باتجاه العميل، ويتوقف عند أول عنوان غير موثوق وفقًا لقواعد الثقة المحددة.

يسمح ذلك باستخراج عنوان العميل من سلسلة الوكلاء، مع عدم الثقة العمياء في جميع العناوين التي تحتوي عليها الترويسة.

يدعم الإعداد أيضًا:

```ts
const app = new App({
  trustProxy: true,
});
```

لكن `true` يثق بجميع القفزات، ولذلك قد يكون غير آمن إذا أمكن للعملاء الاتصال بالتطبيق مباشرةً أو إرسال ترويسات تحويل مزيفة.

اتبع هذه القواعد:

- لا تفعّل الثقة في الوكلاء إلا عند الحاجة إليها.
- حدّد عناوين IP أو النطاقات الشبكية المعروفة بدلًا من الثقة العامة.
- قيّد الوصول الشبكي إلى التطبيق بحيث لا يتمكن العملاء من تجاوز الوكيل الموثوق.
- لا تستخدم عنوان IP المستخرج وحده لاتخاذ قرارات أمنية حساسة دون التأكد من صحة إعدادات الوكيل.

## أبقِ تفاصيل الأخطاء خاصة

قد تكشف رسائل الأخطاء التفصيلية معلومات عن المسارات الداخلية أو قواعد البيانات أو طريقة تنفيذ التطبيق. لذلك، يجب أن تختلف طريقة عرض الأخطاء بين التطوير والإنتاج.

اضبط التطبيق على وضع الإنتاج:

```ts
import { App } from "@barqel/barq";

const app = new App({
  development: false,
});
```

بحسب السلوك الموصوف في Barq، لا تُعرض تفاصيل الأخطاء غير المتوقعة افتراضيًا إلا في وضع التطوير. عند تشغيل التطبيق في الإنتاج، حافظ على هذه الحماية، وتأكد من أن معالج الأخطاء المخصص `onError()` لا يعيد تفاصيل داخلية إلى العميل.

### سجّل التفاصيل على الخادم

يمكنك تسجيل معلومات التشخيص في سجلات الخادم لتسهيل التحقيق في المشكلات، مع إرجاع استجابة عامة ومناسبة للعميل.

على سبيل المثال، ينبغي أن يعرف العميل أن الطلب فشل، لكنه لا يحتاج عادةً إلى معرفة نص استثناء قاعدة البيانات أو مسار ملف داخلي.

تذكّر أن السجلات نفسها قد تحتوي على بيانات حساسة؛ فلا تسجّل كلمات المرور أو رموز الوصول أو الأسرار لمجرد تسهيل التصحيح.

## احمِ الكوكيز والأسرار

قد يعتمد تطبيقك على أسرار توقيع الكوكيز، ومفاتيح API، ومفاتيح TLS. يجب التعامل مع هذه القيم باعتبارها أسرارًا لا تنتمي إلى المستودع البرمجي.

### تخزين الأسرار

اقرأ `cookieSecret` ومفاتيح API ومفاتيح TLS من متغيرات البيئة أو من مدير أسرار مناسب لبيئة التشغيل.

تجنّب وضع القيم الحقيقية مباشرةً في الكود:

```ts
// مثال توضيحي فقط: لا تضع سرًا حقيقيًا في المصدر.
const cookieSecret = process.env.COOKIE_SECRET;
```

تحقّق عند بدء التطبيق من وجود الأسرار المطلوبة وصلاحيتها، بدلًا من تشغيل الخدمة بقيم فارغة أو افتراضية غير آمنة.

استخدم سرًا عالي العشوائية، وضع سياسة لتدويره عند الحاجة، مع مراعاة تأثير تغيير السر في الكوكيز أو البيانات الموقعة الموجودة بالفعل.

### إعدادات الكوكيز

عند استخدام الكوكيز، راجع خيارات الأمان التالية:

- `secure: true`: يطلب إرسال الكوكي عبر اتصالات HTTPS فقط.
- `HttpOnly`: يمنع JavaScript في المتصفح من قراءة الكوكي مباشرةً، ما يقلل فرص سرقتها عبر بعض أنواع هجمات XSS.
- `SameSite`: يساعد على التحكم في إرسال الكوكي مع الطلبات العابرة للمواقع، وفقًا لقيمة الإعداد وسيناريو الاستخدام.

أبقِ `HttpOnly` مفعّلًا ما لم تكن هناك حاجة حقيقية إلى وصول JavaScript للكوكي.

**توقيع الكوكي لا يعني تشفيرها.** فهو يساعد على كشف التعديل غير المصرح به، لكنه لا يجعل محتواها سريًا. لذلك، لا تخزن كلمات المرور أو مفاتيح API أو غيرها من الأسرار داخل قيم الكوكي لمجرد أنها موقّعة.

## قيّد استهلاك الموارد

يمكن أن تؤدي الطلبات الكبيرة أو الاتصالات طويلة الأمد أو التدفق غير المحدود للبيانات إلى استهلاك موارد الخادم. لذلك، اختر حدودًا تناسب طبيعة تطبيقك بدلًا من ترك الموارد مفتوحة بلا داعٍ.

يوفر Barq إعدادات مهمة، منها:

- `maxRequestBodySize`: الحد الأقصى لحجم جسم الطلب.
- `idleTimeout`: المهلة المسموح بها للاتصال الخامل.
- حدود حمولة WebSocket: لتقييد حجم الرسائل التي يقبلها التطبيق.
- الضغط العكسي: للتعامل مع ارتفاع الطلبات عندما تتجاوز القدرة المتاحة.

اضبط القيم وفقًا لحجم البيانات المتوقع، وعدد الاتصالات، والموارد المتاحة. لا توجد قيمة واحدة مناسبة لكل التطبيقات؛ فواجهة API التي تستقبل صورًا كبيرة تختلف عن خدمة لا تتعامل إلا مع رسائل JSON صغيرة.

### الطلبات طويلة الأمد

أبقِ المهلات مفعّلة للطلبات العادية. وإذا كان لديك طلب محدد يحتاج إلى تدفق طويل، فيمكنك استخدام `ctx.disableTimeout()` لتعطيل المهلة لذلك الطلب وفقًا لسلوك Barq.

لا تعطل المهلات لجميع الطلبات لمجرد دعم حالة خاصة؛ لأن الاتصالات المفتوحة بلا حدود قد تستهلك الموارد وتؤثر في بقية المستخدمين.

اختبر حدود الموارد تحت حمل واقعي، وراقب حجم الذاكرة وعدد الاتصالات والوقت المستغرق في معالجة الطلبات.

## تحقّق من بيانات العميل

لا تفترض أن البيانات الواردة صالحة لمجرد أن TypeScript يحدد لها أنواعًا في الكود. فالأنواع العامة لا تتحقق من البيانات أثناء التشغيل.

### معاملات المسار والاستعلام

قيم معاملات المسار والاستعلام نصوص. إذا كنت تتوقع رقمًا أو قيمة محددة، فتحقق منها وحوّلها إلى النوع المطلوب قبل استخدامها.

```ts
app.get("/users/:id", (ctx) => {
  const id = Number(ctx.params.id);

  if (!Number.isSafeInteger(id) || id <= 0) {
    return json({ error: "Invalid user ID" }, 400);
  }

  return json({ id });
});
```

يوضح المثال ضرورة التحقق من المعرّف قبل استخدامه. وهو يفترض توفر `json` في نطاق التطبيق، كما في أمثلة Barq الأخرى.

### أجسام طلبات JSON

استخدم `validateJson()` للتحقق من جسم الطلب باستخدام مخطط متوافق مع Standard Schema أو دالة تحقق مخصصة.

```ts
app.post(
  "/users",
  validateJson(CreateUserSchema, (ctx, body) => {
    return json({ user: body }, 201);
  }),
);
```

بهذه الطريقة، لا يعتمد معالج المسار على افتراضات غير متحققة حول شكل البيانات.

لكن التحقق من البنية لا يغني عن التحقق من الصلاحيات أو قواعد العمل. فحتى إذا كان جسم الطلب صالحًا من حيث الأنواع، فقد لا يكون المستخدم مخولًا لتنفيذ العملية أو الوصول إلى المورد المطلوب.

## النشر في بيئة الإنتاج

قبل نشر التطبيق، تأكد من أن عملية التشغيل وإعدادات الشبكة والأسرار والمهلات تتناسب مع بيئة الإنتاج.

### شغّل التطبيق تحت إشراف عملية

شغّل نقطة دخول Bun باستخدام مشرف عمليات أو منصة حاويات تستطيع إعادة تشغيل العملية عند فشلها. يساعد ذلك على استعادة الخدمة بعد الأعطال غير المتوقعة، لكنه لا يغني عن مراقبة الأخطاء وفهم أسبابها.

تأكد أيضًا من أن بيئة التشغيل تتعامل مع إشارة `SIGTERM`، التي تُستخدم عادةً لطلب إنهاء العملية بطريقة منظمة.

### أوقف التطبيق بصورة منظمة

يوفر Barq الدالة `app.stop()` للمساعدة على إيقاف التطبيق وتفريغ الطلبات وفقًا لسلوك الإطار.

عند إيقاف الخدمة، اتبع ترتيبًا واضحًا:

1. أوقف استقبال العمل الجديد بالطريقة التي تدعمها بيئة التشغيل.
2. امنح الطلبات الجارية فرصة مناسبة للانتهاء.
3. استدعِ آلية الإيقاف المناسبة في Barq.
4. تأكد من إنهاء العملية ضمن المهلة التي تحددها منصة التشغيل.

تحقّق من تفاصيل دورة حياة `app.stop()` في إصدار Barq الذي تستخدمه، ولا تفترض أنه يوقف جميع الموارد الخارجية التي أنشأها التطبيق، مثل اتصالات قواعد البيانات أو العمال الخلفيين، ما لم تكن موثقة ضمن سلوكه.

### إعداد TLS

يمكنك إعداد TLS مباشرةً في Bun، أو إنهاء اتصال TLS عند وكيل عكسي موثوق أمام التطبيق.

في الحالتين:

- لا تحفظ المفاتيح الخاصة داخل المستودع.
- امنح الوصول إلى ملفات الشهادات والمفاتيح للعمليات التي تحتاج إليها فقط.
- راجع تجديد الشهادات وانتهاء صلاحيتها.
- إذا أنهيت TLS عند وكيل عكسي، فتأكد من حماية الاتصال بين الوكيل والتطبيق وفقًا لمتطلبات بيئتك.

## قائمة مراجعة قبل الإطلاق

- [ ] ضبط `development: false`.
- [ ] تحديد الوكلاء الموثوقين فقط عند الحاجة إلى `trustProxy`.
- [ ] تخزين الأسرار خارج المستودع والتحقق من وجودها عند بدء التشغيل.
- [ ] مراجعة إعدادات الكوكيز، خصوصًا `Secure` و`HttpOnly` و`SameSite`.
- [ ] تحديد أحجام الطلبات والمهلات وحدود رسائل WebSocket.
- [ ] التحقق من مدخلات العميل باستخدام `validateJson()` أو تحقق صريح مناسب.
- [ ] التأكد من عدم تسريب تفاصيل الأخطاء أو الأسرار إلى العملاء والسجلات.
- [ ] اختبار إيقاف التطبيق وإعادة تشغيله بعد الفشل.
- [ ] التحقق من إعداد TLS وتجديد الشهادات.

أمان الإنتاج ليس خيارًا واحدًا أو إعدادًا منفردًا. إنه مجموعة من القرارات المتكاملة التي تحدد من يستطيع الوصول إلى التطبيق، وما البيانات التي يقبلها، وكيف يتعامل مع الأخطاء، ومقدار الموارد التي يسمح لكل طلب باستهلاكها.
