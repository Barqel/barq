# البداية السريعة

هل تريد تجربة Barq ورؤية خادمك الأول يعمل؟ في هذا الدليل، ستبني تطبيق HTTP صغيرًا، وتشغّله باستخدام Bun، ثم تختبر مساراته وتتعرف على كيفية قراءة بيانات الطلبات.

سنبدأ بأبسط مثال، ثم نضيف مسارًا يعرض حالة الخدمة، ومسارًا يستقبل معرّف مستخدم ومعامل استعلام، وأخيرًا مسارًا يقرأ جسم طلب بصيغة JSON.

بحلول نهاية الدليل، ستكون قد تعرّفت على الأساسيات التي تحتاج إليها للانتقال إلى بناء تطبيق حقيقي.

## 1. أنشئ التطبيق

أنشئ الملف `src/index.ts` داخل مشروعك، ثم أضف الكود التالي:

```ts
import { App, json, text } from "@barqel/barq";

const app = new App();

app.get("/", () => text("Barq is running"));
app.get("/health", () => json({ ok: true }));

app.get("/users/:id", (ctx) => {
  return json({
    id: ctx.params.id,
    view: ctx.queryParam("view"),
  });
});

const server = app.listen(Number(Bun.env.PORT ?? 3000));

console.log(`Listening on http://localhost:${server.port}`);
```

هذا التطبيق صغير، لكنه يوضح عدة أجزاء أساسية من Barq. دعنا نفهمها خطوة بخطوة.

### إنشاء التطبيق

```ts
import { App, json, text } from "@barqel/barq";

const app = new App();
```

يستورد السطر الأول ثلاث واجهات عامة من Barq:

- `App` لإنشاء تطبيق HTTP وتسجيل المسارات عليه.
- `json()` لإنشاء استجابة تحتوي على بيانات JSON.
- `text()` لإنشاء استجابة نصية.

بعد ذلك، ينشئ `new App()` نسخة التطبيق التي ستسجّل عليها المسارات وتضبط من خلالها الخادم.

### إنشاء أول مسار

```ts
app.get("/", () => text("Barq is running"));
```

يسجّل هذا السطر مسارًا يستقبل طلبات HTTP من نوع `GET` إلى `/`.

عندما يطلب المتصفح العنوان `http://localhost:3000/`، يعيد التطبيق النص التالي:

```text
Barq is running
```

تُستخدم `GET` عادةً لقراءة البيانات أو طلب مورد من الخادم. أما `/` فهو المسار الرئيسي للموقع أو الخدمة.

### إضافة مسار لفحص الحالة

```ts
app.get("/health", () => json({ ok: true }));
```

يعيد هذا المسار استجابة JSON:

```json
{
  "ok": true
}
```

يمكن استخدامه في اختبارات التشغيل أو أنظمة مراقبة الخدمة للتحقق من أن المسار يستجيب.

لكن انتبه: نجاح هذا المسار لا يعني بالضرورة أن قاعدة البيانات وجميع الخدمات الخارجية تعمل بصورة سليمة. إذا كانت الخدمة تعتمد على هذه المكونات، فقد تحتاج إلى فحوص إضافية.

## 2. قراءة معاملات المسار والاستعلام

أضفنا المسار التالي إلى التطبيق:

```ts
app.get("/users/:id", (ctx) => {
  return json({
    id: ctx.params.id,
    view: ctx.queryParam("view"),
  });
});
```

يستخدم هذا المثال نوعين مختلفين من البيانات الواردة في عنوان الطلب.

### معامل المسار: `ctx.params.id`

في المسار `/users/:id`، تمثل `:id` قيمة متغيرة داخل عنوان URL.

على سبيل المثال، عند إرسال طلب إلى:

```text
/users/42
```

تكون قيمة `ctx.params.id` هي النص `"42"`.

يمكنك استخدام هذه القيمة لتحديد المستخدم الذي تريد البحث عنه أو عرضه. لكن هذا المثال يعيد القيمة نفسها فقط، ولا يتصل بقاعدة بيانات ولا يتحقق من وجود المستخدم.

### معامل الاستعلام: `ctx.queryParam("view")`

يمكن أن يحتوي عنوان URL على معاملات استعلام بعد علامة `?`.

مثلًا:

```text
/users/42?view=compact
```

في هذا الطلب:

- `42` هي قيمة معامل المسار `id`.
- `compact` هي قيمة معامل الاستعلام `view`.

تعيد `ctx.queryParam("view")` قيمة المعامل بوصفها نصًا إذا كان موجودًا. وإذا لم يكن موجودًا، فقد تكون النتيجة `undefined` وفقًا لواجهة Barq المستخدمة.

لذلك، لا تفترض أن معامل الاستعلام موجود دائمًا، ولا تستخدم قيمته قبل التحقق منها إذا كانت مطلوبة لتنفيذ العملية.

### لماذا تكون القيم نصوصًا؟

يستنتج TypeScript أن `ctx.params.id` نص، كما أن معاملات الاستعلام تُقرأ عادةً كنصوص. حتى لو بدت القيمة رقمًا مثل `"42"`، فهي ليست رقمًا تلقائيًا.

إذا احتجت إلى رقم، فحوّل القيمة وتحقق من صلاحيتها قبل استخدامها:

```ts
const id = Number(ctx.params.id);

if (!Number.isSafeInteger(id) || id <= 0) {
  return json({ error: "Invalid user ID" }, 400);
}
```

هذا المثال يوضح التحقق من القيمة بعد تحويلها إلى رقم صحيح موجب آمن. أما كيفية إرجاع الاستجابة من داخل المسار، فيجب أن تتوافق مع واجهة Barq الفعلية المستخدمة في تطبيقك.

**القاعدة المهمة:** لا تخلط بين استنتاج الأنواع في TypeScript والتحقق من صحة البيانات التي تصل إلى الخادم. البيانات الواردة من الطلبات تحتاج إلى تحقق مناسب أثناء التشغيل.

## 3. شغّل الخادم

من جذر المشروع، نفّذ الأمر التالي:

```sh
bun run src/index.ts
```

يطلب هذا الأمر من Bun تشغيل ملف التطبيق مباشرة.

في نهاية الكود، نستخدم:

```ts
const server = app.listen(Number(Bun.env.PORT ?? 3000));

console.log(`Listening on http://localhost:${server.port}`);
```

يقرأ التعبير `Bun.env.PORT ?? 3000` قيمة متغير البيئة `PORT`، أو يستخدم `3000` إذا لم يكن المتغير محددًا. ثم يحوّل `Number()` القيمة إلى رقم ويمررها إلى `listen()`.

بعد بدء الخادم، تعرض رسالة السجل المنفذ الذي يستخدمه الخادم عبر `server.port`.

إذا كانت قيمة `PORT` غير رقمية أو كان المنفذ غير متاح، فقد يفشل تشغيل الخادم؛ لذلك استخدم قيمة صحيحة وتأكد من أن المنفذ متاح.

## 4. اختبر المسارات

اترك الخادم يعمل، ثم افتح طرفية أخرى ونفّذ الأوامر التالية.

### الصفحة الرئيسية

```sh
curl http://localhost:3000/
```

الاستجابة المتوقعة:

```text
Barq is running
```

### فحص الحالة

```sh
curl http://localhost:3000/health
```

الاستجابة المتوقعة:

```json
{"ok":true}
```

### بيانات المستخدم

```sh
curl 'http://localhost:3000/users/42?view=compact'
```

الاستجابة المتوقعة:

```json
{
  "id": "42",
  "view": "compact"
}
```

قد يختلف تنسيق المسافات في JSON بحسب طريقة عرض الاستجابة، لكن القيم نفسها ينبغي أن تكون متطابقة.

لاحظ أن `id` يظهر كنص، وليس رقمًا. هذا سلوك مقصود في المثال؛ إذ يعيد المسار قيمة معامل URL دون تحويلها.

إذا شغّلت الخادم على منفذ مختلف، فاستبدل `3000` بالمنفذ الفعلي الذي يظهر في رسالة التشغيل.

## 5. استقبال جسم طلب JSON

تحتاج بعض المسارات إلى استقبال بيانات من العميل، مثل بيانات نموذج أو معلومات يراد حفظها. في هذه الحالة، يمكن أن يرسل العميل البيانات داخل جسم الطلب بصيغة JSON.

أضف المسار التالي إلى التطبيق:

```ts
app.post("/echo", async (ctx) => {
  const payload = await ctx.json<unknown>();

  return json({ received: payload }, 201);
});
```

يتكون المثال من ثلاث خطوات:

1. يسجّل `app.post()` مسارًا يستقبل طلبات `POST` إلى `/echo`.
2. يقرأ `await ctx.json<unknown>()` جسم الطلب ويحلل JSON إلى قيمة.
3. يعيد `json()` البيانات المستلمة داخل الخاصية `received`، مع رمز الحالة `201`.

استخدام `201` شائع عندما تؤدي العملية إلى إنشاء مورد جديد. أما في هذا المثال، فلا يُنشأ مورد فعلي؛ فالاستجابة تعيد البيانات فقط. إذا كان هدفك مجرد استقبال البيانات وإعادتها دون إنشاء مورد، فقد يكون رمز `200` أو رمز آخر مناسبًا بحسب السلوك المقصود.

### ماذا يعني `unknown` هنا؟

```ts
const payload = await ctx.json<unknown>();
```

يعني `unknown` أن TypeScript لا يفترض شكل البيانات المستلمة. وهذا أكثر أمانًا من منح البيانات نوعًا محددًا دون التحقق من أنها تطابقه.

لكن النوع العام في `ctx.json<unknown>()` لا يتحقق من صحة بنية البيانات أثناء التشغيل. كما أن نجاح تحليل JSON لا يعني أن الحقول المطلوبة موجودة أو أن قيمها صحيحة.

### التحقق من البيانات قبل استخدامها

إذا كان التطبيق يعتمد على شكل محدد من البيانات، فتحقق من بنيتها قبل استخدامها في منطق التطبيق أو حفظها في قاعدة البيانات.

يوفر Barq واجهة `validateJson()` لهذا الغرض عند استخدامها مع محلل يفحص قيمة من النوع `unknown`.

راجع دليل [التحقق من JSON](/ar/basics/validation/) لمعرفة كيفية تطبيق التحقق على بيانات الطلبات.

**تذكّر:** تحليل JSON يجيب عن سؤال «هل يمكن قراءة الجسم بوصفه JSON؟»، بينما التحقق من البيانات يجيب عن سؤال «هل تتوافق هذه البيانات مع الشكل والقواعد التي يتطلبها التطبيق؟».

## 6. ماذا بعد؟

أصبحت لديك الآن نقطة بداية يمكنك البناء عليها. انتقل إلى الموضوع المناسب لاحتياجاتك:

- [أنماط المسارات](/ar/basics/routing/) — تعرّف على تعريف المسارات وتنظيمها والتعامل مع معاملات URL.
- [مجموعات المسارات](/ar/basics/routing/) — تعلّم كيفية تجميع المسارات المرتبطة تحت بادئة مشتركة، وفقًا للواجهات التي يدعمها Barq.
- [الوسائط البرمجية (Middleware)](/ar/basics/middleware/) — أضف سلوكًا مشتركًا أثناء معالجة الطلبات.
- [معالجة الأخطاء](/ar/basics/errors/) — تعامل مع الأخطاء والطلبات التي لا تطابق أي مسار.
- [التحقق من JSON](/ar/basics/validation/) — تحقّق من بيانات الطلبات قبل استخدامها.
